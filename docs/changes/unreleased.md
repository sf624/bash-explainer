# Unreleased changes, in detail

The short list is in [CHANGELOG.md](../../CHANGELOG.md#unreleased).

## New

### Known values read in the command's language

A variable whose value the script makes known is read in the language of the command that uses it (#790, docs/design/known-values.md, step 2: the use).

- **What is read.** A word that is only a copy of a variable, `$x`, `${x}`, `"$x"` or `"${x}"`, where the panel already shows the variable's value ("Value here, from the script"), in a place the command reads in a language of its own: grep's pattern (BRE, `-E`, `-P`, `-e`), sed's script (`sed -n "$s" f`, `sed -e "$s"`), an awk program, a jq filter, a printf format, `date "$fmt"`, tr's sets. The rows of the reading are under the value, in the panel, the hover's card, Markdown, the command line and `--format json`: `re='^[A-Z][0-9]+$'; grep -E "$re" ids.txt` gets the rows of `^`, `[A-Z]`, `[0-9]`, `+` and `$`, as `grep -E '^[A-Z][0-9]+$' ids.txt` does, and the example of matching lines. The role of the word gets the reader's note too ("search pattern (regex) — extended regex (ERE)"). Before, the value was shown but not read, and `sed -n "$s" f` said that what the script does depends on the value of `$s`.
- **Errors.** An error in the value is an Error of the line, in Problems and `--check`, as for the literal: `re='[a'; grep -E "$re" f` says "No `]` closes this `[`: `grep` stops with an error (status 2)".
- **`[[ $x =~ $re ]]`.** An unquoted `$re` or `${re}` on the right of `=~`, where the value is known, is read as the ERE bash reads, as a literal right side is: `re='^[0-9]+$'; [[ $1 =~ $re ]]` gets the rows of `^`, `[0-9]`, `+` and `$` under the value, and the example of matching strings. `[[ ]]` neither splits nor globs, so the value is the regex whatever it holds. An error in it (`re='[a'`) is an Error of the line, as for the literal. The quoted `"$re"` is still text bash looks for as it is, and gets no rows.
- **Unquoted values.** `grep -E $re ids.txt` is read as grep gets it where no file name matches: a line above the rows says so. A value with a space or a tab, a value bash splits (`x='-e s/a/b/'; sed $x f`), an absolute glob (`p='/[A-Z]+/p'; sed -n $p f`), and nullglob or failglob on or maybe on are read as before.
- **Not yet.** A value inside a larger word (`"s/$from/x/"`, `-e"$p"`), another form of expansion (`${p%x}`), a command another command runs (`sudo grep -E "$re" f`, `find -exec grep …`, bats' `run grep …`) and find's own tests (`find -name "$p"`) are read as before. The example is not made yet where it needs another word that is a known value: the `-e` of sed and grep, awk's options, printf's format and tr's sets (the rows are there).
- **The assignment.** The line that sets the value shows how its uses read it (step 5). With one reading, the string gets its rows, as a prompt string's (`PS1='\u@\h'`) and a literal's: `re='^[A-Z][0-9]+$'` followed by `grep -E "$re" ids.txt` gets the rows of `^`, `[A-Z]`, `[0-9]`, `+` and `$`, and the text "read as an extended regex (ERE) by `grep -E`, line 2". Several uses that read it alike are one reading, with each line named ("lines 4 and 9", "lines 2–9"; past three, "lines 4, 9, 12 and 2 more"). The text says each language or flavour once, with its commands as written (with their options: "by `grep -m 1 -E`"), the first three of them ("by `grep -q`, `grep -c`, `grep -v` and 5 more, lines 2–9"), and past three readings "in 2 more ways". Uses that read it differently (`grep "$re"` and `grep -E "$re"` on `^a+`) give no rows and no warning, only each command and its flavour: "read as a basic regex (BRE) by `grep` (line 4) and as an extended regex (ERE) by `grep -E` (line 9)". A use that finds an error in the value is named ("`grep -E` reads it as an extended regex (ERE) on line 2 and finds an error there"); the Error is said once, on the use's line. A use is one that this assignment's value reaches, whatever the text order: a function defined above it and called after it counts, and a second assignment before the use takes its place. A value that globs, used unquoted, adds "where no file name matches it" to its lines. Where bash removes a backslash first (`re="a\\.b"`), the assignment line says so. `PS1`, `PS4` and the other prompt strings keep bash's own reading. In a host file (Markdown, bats) the lines are the document's. The assignment line has no example: the uses' lines have them.
- **What stays out.** The uses of section "Not yet" above, and a use that `read`, `printf -v`, `mapfile`, a `for` over several words or a value of the environment reaches. Since #826, such a command elsewhere no longer hides the value from the other uses (section "Values beside an unset, a bare `local` or a loop" below).

## Changed

### Values beside an unset, a bare `local` or a loop

A variable keeps its value where the model already follows its other writes (#826; docs/design/known-values.md, "What step 4 found").

- **Now shown.** The value at a use ("Value here, from the script"), the reading of a known value in the command's language, the conditions the panel says are always true or false, and the code it says never runs, also in a script that elsewhere runs `unset re`, a bare `local re` or `declare re` in a function, `for re in …`, `read re`, `printf -v re` or `mapfile re`. So `f() { local re; re='^a'; grep -E "$re" g; }; f` (the form ShellCheck's SC2155 recommends), `re='^a'; grep -E "$re" g; f() { local re; }`, `re='^a'; grep -E "$re" g; for re in x; do :; done` and `re='^a'; grep -E "$re" g; unset re` get the reading of `^a`. Before, one such command anywhere, even in a function no call reaches, hid every value of the variable.
- **What each gives.** After `unset re`, and in a function after `local re`, the value is the empty string (`${re-u}` gives `u`); the value before the function was called comes back when it returns, and a function it calls sees the local (dynamic scope). After `for re in x`, `re` is `x`; after a loop over several words, the last one, unless the body changed it (`for x in a; do x=z; done` leaves `z`). After `read`, `printf -v` and `mapfile`, the value is not known. A use that two of these reach with different values has none. `unset` of a local of a calling function shows what the nearest such local hides (`h() { local x=7; f; }`, where `f` makes its own `x` and calls a function that unsets it), and `unset x` in a function called as `x=t f` shows the `x` from before the call; a `local` made on some paths only, or again on a pass of a loop, gives no value after it where the paths differ. Before, these could show a wrong value.
- **Changed in the corpus.** `for a in $*` elsewhere in the web page's sample no longer hides `a=1` from `[ "$a" -eq 1 -a "$b" -eq 2 ]`; after `for D in a; do :; done`, `rm -rf $D/x` no longer warns that `D` may be empty (it is `a`).

### The glob in an unquoted value a command reads

- **Said once.** The caveat on an unquoted value a command reads as data (`re='^[A-Z][0-9]+$'; grep -E $re ids.txt`) says that bash also reads it as a glob pattern, with the parts that make it one (its `[A-Z]`, `[0-9]`), before `grep` gets it; in an sh or dash script, "the shell". The value's line says it the same way, whether the value is read in the command's language or not (`sudo grep -E $re f`, `find . -exec grep -E $re {} +`, `xargs grep -E $re`). The argument's row no longer says it a third time. Before, the three said "it is a glob pattern". Where no note is said (bats' `run grep -E $re f`), the row says it as before.

## Fixed

### Examples under nocasematch

- **Regex.** With `shopt -s nocasematch` on, the example of `[[ $ans =~ ^(y|yes)$ ]]` ignores case as bash does: `Y` and `YES` are in "Matches", not in "Does not match". Where nocasematch may be on (`if …; then shopt -s nocasematch; fi`), there is no example. Before, it matched case-sensitively whatever the option.
- **Patterns.** The same for `[[ $x == pat ]]` and `case`: no example where nocasematch may be on. With it on, `[[:upper:]]` and `[[:lower:]]` in a pattern get no example, since bash does not fold those classes in a pattern (it does in `=~`).
- **Classes.** With nocasematch on, `[[:upper:]]` and `[[:lower:]]` in a `[[ == ]]` or `case` pattern get no example, and under nocaseglob none for a file pattern (`shopt -s nocaseglob; ls [[:upper:]]*` lists only `Abc` of `abc Abc xyz`): bash folds the ranges of `[a-z]` but not those classes.
- **Replacements.** The same fix reaches `${x//pat/rep}` under nocasematch: `shopt -s nocasematch; x=aBc; y=${x//[[:lower:]]/X}` was shown as `XXX`; bash gives `XBX`, and the value is now left unknown.
- **After `source`, `.` or `eval`.** nocasematch is taken as set before (a sourced file almost never turns it on), as the examples always did; the plain-text reading of a pattern (`[[ $x == y ]]`) now does too. Before, it gave up there.

### Functions called with a prefix assignment

- A call such as `MODE=a helper "$1"` was worked out again at every call, so a chain of functions that each call the next twice this way doubled the work at each level: 18 levels (about 55 lines) took 18 s. A call made again from the same state now reuses the first one, as a call without a prefix assignment does, and the chain takes a few milliseconds. On nvm.sh, the most states a line was explained with went from 356 to 21.
- Such a call now counts towards the four walks of a function, as a plain call does: a function called from more than four different states has its later calls guessed (what the body changes is taken as not known).
