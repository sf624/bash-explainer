# Roadmap

What is planned, in the order agreed with the maintainer, and what waits on a decision. The design documents hold the details of each plan ([docs/design/README.md](design/README.md) lists them with their status); this page holds the order.

Keep it current:

- Read it before starting new work, and before proposing any.
- Update it in the same PR that starts, finishes or drops an item. Move a finished item to "Done lately" with its PRs.
- Add an item when the maintainer agrees to a plan, or asks for something that will not be done at once. An idea nobody agreed to goes under "Not decided".

## Now

First step in review: made-up output in the real layout for `ps`, `ls`, `df -h`, `who`, `env` (`CommandSpec.layouts`), and input labels that name the command a pipe brings them from; each section marks what the next stage reads (grep's and sed's matches, awk's and cut's fields, sort's keys), and a wide table starts scrolled to its first mark. ## Next, in this order

1. Audit Reading against the Bash Reference Manual, section by section (chapter 3 first): every construct Reading shows is named and grouped as the manual does, and every operator and reserved word appears in the tree. Findings fixed as explanation bugs, with tests against bash or bash-ast. Raised by the maintainer 2026-10-26. Chapter 3 done: 3.1 to 3.4 in #400, 3.5 to 3.7 in #409 (the findings in docs/changes/unreleased.md, "Reading as the Bash manual reads it"; test/reading-manual.test.ts). Left from chapter 3: the braces of `{a,b}` alone as a row (3.5.1), which needs the parser to make a brace expression of it (`braceList` in src/syntax/adapters/unbash.ts makes one only next to a sequence); waits on the maintainer. Chapter 4 done (the builtins: each cites its section and 4.4 for a special builtin, their options and operands as bash reads them, `exec` with no command; #415). Left from chapter 4: the badge of a special builtin says "builtin" (its tooltip names the class; a word of its own waits on the maintainer); the strings `mapfile -C`, `bind -x` and `complete -C` run are not read as scripts (`trap`'s and `eval`'s are). Next: chapters 5 and 6, section by section in the same way (5: the shell variables, 6: the rest of bash's features). Known there: the index of an array (6.7) is one name row (`a[i+1]`), with no rows for its brackets or its arithmetic; 6.4 and 6.5 were checked with `[[ ]]` and arithmetic in #400.
2. New pitfalls from the usability test of October 2026, each a style check in src/pitfalls.ts (or a catalog note where it states a fact), with tests against bash: a download piped into a shell (`curl … | sh`, `wget -O- … | bash`): the script runs unseen and may run half-downloaded; `trap '…' INT` (or TERM) whose handler does not exit: the script goes on after Ctrl+C; `cond && cmd` as the last command of a function under `set -e` (or of a script): when `cond` fails, the function returns its status 1, and `set -e` stops the caller (`f() { false && :; }; set -e; f; echo after` never prints `after`), although nothing failed; an array joined in an assignment (`a=$@`, `x=${arr[@]}`, ShellCheck SC2124): the elements become one string (the explanation says so since #398; the pitfall suggests `a=("$@")` or `"${arr[*]}"`). `ssh -o StrictHostKeyChecking=no` is already explained as a caveat (#398). Decided by the maintainer 2026-10-27.
3. The basis of an explanation, as data, after the analyzer is thinned: an explanation that rests on bash's behaviour rather than the manual gets a chip ("Not in the manual · checked with bash 5.2", or "Differs from the manual"), and a folded "Try it in your terminal" with a command and its output, taken from the probe that checks it in CI (look A of the prototype on branch `proto/basis`). A setting turns the chips and the try-its off. Other kinds of basis (another tool's spec, convention) are data only for now.
4. bash 5.3, step 3 of [design/bash-versions.md](design/bash-versions.md), the walk of `${ }` (the substitution walk moved out of src/semantics/walk/walker.ts first), and the POSIX-mode rows of step 6.
5. Run-based oracles, steps 2–10 of [design/oracles.md](design/oracles.md): argv capture, checking suggestions in bash, the normal-forms audit.
6. Values of a whole word (`"$dir/$f"`), arrays, and per-call values in functions: after trust per position (item 8); the corpus shows little gain ([design/expansion-values.md](design/expansion-values.md), section 6).
7. The leftovers of the small gaps (A3): the readers of arguments that have no shell at hand (`argWord` in src/semantics/env.ts, effects.ts, vars.ts, src/idioms.ts, src/semanticFacts.ts) count the words of a brace expansion in every shell; and a BSD letter of ps with a value takes the rest of its word (`ps opid,comm`, `ps Uroot`), which the argument interpreter reads as the next word.
8. Trust per position instead of per script: a `source`, `eval` or `$cmd` makes variables untrusted only on the paths after it, not in the whole file. Shared with conditions and dead code. Design: [design/trust-per-position.md](design/trust-per-position.md) (deferred; step 0 done). Its step 0, done (#382), fixed wrong values and dead code of today's model found on the way (`-v` of a name not known, reads of a nameref whose target is not known, `${x@P}`, a bare `declare n` from the environment read as arithmetic, `compgen -W`, `fc -s`, recursive calls, `enable -n exit`). Steps 1–4 deferred: the measured gain is small (34 → 45 values on 358 real scripts). (Measured with a prototype: every function body is lost after a taint in the main flow; section 10 there.) Decided by the maintainer 2026-10-26.
9. A usability test with 5 users gives an average of 9/10 or more. The users are personas such as a beginner, a certification learner, a sysadmin, a developer and a UX designer, as in the survey of October 2026. Measured the same way: fresh agents with no project context judge screenshots or the running page, and each gives an overall score out of 10. Starts once the items before it are done. Decided by the maintainer 2026-10-27.

## Waiting on the maintainer

- Reading of `{a,b}` alone (item 1, 3.5.1): its braces and `,` are rows only next to a sequence (`{a,b}{1..2}`), where the unbash adapter makes a `brace_expression`. Proposal: make one for every brace list bash expands (unbash already gives the part), and move the readers of brace words (src/semantics/brace.ts, src/explain/words.ts, src/argv/words.ts, src/highlight.ts, src/dialect.ts) to it, with the bash-ast and corpus tests. A change of the syntax model, so it waits on a yes.

## Not decided

- Web page follow-ups of opening and saving files (#358): "Save as…" for an opened file; a CRLF→LF conversion (the `crlf` warning says to convert, and the page has no way to); the file name in share links.
- Variable kinds: say what a variable name is where it is used, as the name kinds do for commands: a shell variable, an exported (environment) variable that child processes see, a special parameter (`$?`, `$@`), a function's local, or one bash sets itself (`RANDOM`, `SECONDS`). The model already has the attributes (`shellState`). It answers the same question as `sudo echo`: what a child process sees.
- Makefile recipes: make execs simple lines directly; the badge should say program, run by make. (GNU make runs a recipe line with no shell syntax without a shell: `echo -e x` execs `/bin/echo`, which prints `-e x`; the badge says builtin.)
- `which` against `type` and `command -v`: a sentence saying that `which` looks only for programs on PATH, while `type` and `command -v` also find builtins, functions and aliases, so their answers can differ.
- A third language. Today ja/en pairs sit in about 100 files (75% in src/dict specs, the message catalog, ~2,200 inline pairs in code), the language list is repeated in ~10 places, and about 12 copies of `lang === 'ja' ? ja : en` would show any new language as English without a warning. Proposed cheap steps first (one `LANGS` list that the settings enum, CLI, web menu and build derive from; keyed `Text` records and one `pick` with an English fallback instead of positional `(ja, en)`; inline texts moved into per-module catalogs; a CONTRIBUTING section listing what to touch), and per-language overlay files (`locales/<lang>/…`, keyed by message id or command and option) only when someone offers a language. Raised 2026-10-26; after the current Now/Next.
