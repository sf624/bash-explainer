# Roadmap

What is planned, in the order agreed with the maintainer, and what waits on a decision. The design documents hold the details of each plan ([docs/design/README.md](design/README.md) lists them with their status); this page holds the order.

Keep it current:

- Read it before starting new work, and before proposing any.
- Update it in the same PR that starts, finishes or drops an item. Move a finished item to "Done lately" with its PRs.
- Add an item when the maintainer agrees to a plan, or asks for something that will not be done at once. An idea nobody agreed to goes under "Not decided".

## Next, in this order

1. Every pitfall stated as a problem, with its level and its range, once the thinned analyzer gives note nodes ([design/note-levels.md](design/note-levels.md), "The bridge"): the views then read the level from the node, not from the note's mark (`noteLevel`, `splitNote`). Today only the pitfalls of src/pitfalls.ts and src/wordfacts.ts are problems; the other notes found on a node already carry its range (`LineExplanation.anchors`, for the part hover). Decided with the hover ([design/hover.md](design/hover.md)); the other notes stay out of the diagnostics until then.
2. Lists as the manual reads them (3.2.4): a list is pipelines separated by `;`, `&`, `&&` or `||`, where `&&` and `||` bind tighter than `;` and `&`. Today only an `&&`/`||` group is a node, labelled 'Command list' (the manual calls it an AND or OR list), and `a; b & c && d` gets no list node at all; Reading's tree leaves out `;`. Show the whole list with its four operators and their precedence (what `&` applies to), in Meaning and Reading. Raised by the maintainer 2026-10-26.
3. Audit Reading against the Bash Reference Manual, section by section (chapter 3 first): every construct Reading shows is named and grouped as the manual does, and every operator and reserved word appears in the tree. Findings fixed as explanation bugs, with tests against bash or bash-ast. Raised by the maintainer 2026-10-26.
4. The shebang line: today `#!/usr/bin/env bash` says "run this script with `/usr/bin/env bash`" unconditionally. Say that it takes effect only when the file is run as a program (`./script.sh`: the kernel's execve(2), "Interpreter scripts", starts the interpreter with the script's path, and bash does it itself on systems that do not); with `bash script.sh`, `sh script.sh` or `source`, it is a comment. Cite execve(2) as well as §3.8 (a reference kind other than the bash manual: see the basis item). Also give the shebang its own colour, distinct from comments, in the panel (Meaning and Reading token kind), the semantic highlighting (a custom token type with `superType: comment`, so that themes without a rule still colour it as a comment) and the web editor; to bash it stays a comment, and the explanation says so. Asked by the maintainer 2026-10-26.
5. Trust per position instead of per script: a `source`, `eval` or `$cmd` makes variables untrusted only on the paths after it, not in the whole file. A corpus of 536 real scripts (23 repositories) showed 60% of scripts wholly blind, and 651 of ~790 missed constant reads lost to it only. Shared with conditions and dead code, so they gain too. Design document first.
6. Values of top-level constants inside functions (assigned once before any call, no other writer).
7. The basis of an explanation, as data, after the analyzer is thinned: an explanation that rests on bash's behaviour rather than the manual gets a chip ("Not in the manual · checked with bash 5.2", or "Differs from the manual"), and a folded "Try it in your terminal" with a command and its output, taken from the probe that checks it in CI (look A of the prototype on branch `proto/basis`). A setting turns the chips and the try-its off. Other kinds of basis (another tool's spec, convention) are data only for now.
8. bash 5.3, step 2 of [design/bash-versions.md](design/bash-versions.md): fix the explanations of `printf %#q` and `%ls` first (they are wrong today), then steps 3–7.
9. Run-based oracles, steps 2–10 of [design/oracles.md](design/oracles.md): argv capture, checking suggestions in bash, the normal-forms audit.
10. Pipeline examples: show the shape of the input each stage reads (item 3 of the external review of October 2026).
11. bats, what [design/bats.md](design/bats.md) lists as not done: a model per test (its own process, `set -e`), hooks, bats-assert, tags.
12. Small gaps of the specs and the models ([design/semantics.md](design/semantics.md), A3): procps reads digits after BSD letters as PIDs (`ps u1`); GNU tar reads a first word without a dash as letters (`tar vf a.tar`). The word model (`wordMeaning`, src/semantics/words.ts) applies brace expansion in every shell: in a `#!/bin/dash` script, `echo {a,b}` is said to expand, though dash (like POSIX sh) has no brace expansion and prints `{a,b}` (noted in #332; only the redirection target checks the dialect, `braceWorks` in src/explain/redirections.ts).
13. Brace expansion examples: show that the result is several words (`echo 1 4 7 10`), not one (`echo "1 4 7 10"`). Today "Resulting words" lists one word per line, which reads like the command's output. Find a look that shows separate words (word chips, or the expanded command line), and, where the output is known (`echo`, `printf`), the output too. Agreed 2026-10-25, to do after the analyzer.
14. Dead code faded in the editor: a `DiagnosticTag.Unnecessary` hint on a statement that never runs (`shellState(...).dead(n)`), with its message in the catalog and on every surface ([design/highlighting.md](design/highlighting.md)).
15. Values of a whole word (`"$dir/$f"`), arrays, and per-call values in functions: after items 5 and 6; the corpus shows little gain ([design/expansion-values.md](design/expansion-values.md), section 6).

## Not decided

- Web page follow-ups of opening and saving files (#358): "Save as…" for an opened file; a CRLF→LF conversion (the `crlf` warning says to convert, and the page has no way to); the file name in share links.
- Variable kinds: say what a variable name is where it is used, as the name kinds do for commands: a shell variable, an exported (environment) variable that child processes see, a special parameter (`$?`, `$@`), a function's local, or one bash sets itself (`RANDOM`, `SECONDS`). The model already has the attributes (`shellState`). It answers the same question as `sudo echo`: what a child process sees.
- Makefile recipes: make execs simple lines directly; the badge should say program, run by make. (GNU make runs a recipe line with no shell syntax without a shell: `echo -e x` execs `/bin/echo`, which prints `-e x`; the badge says builtin.)
- `which` against `type` and `command -v`: a sentence saying that `which` looks only for programs on PATH, while `type` and `command -v` also find builtins, functions and aliases, so their answers can differ.
- A third language. Today ja/en pairs sit in about 100 files (75% in src/dict specs, the message catalog, ~2,200 inline pairs in code), the language list is repeated in ~10 places, and about 12 copies of `lang === 'ja' ? ja : en` would show any new language as English without a warning. Proposed cheap steps first (one `LANGS` list that the settings enum, CLI, web menu and build derive from; keyed `Text` records and one `pick` with an English fallback instead of positional `(ja, en)`; inline texts moved into per-module catalogs; a CONTRIBUTING section listing what to touch), and per-language overlay files (`locales/<lang>/…`, keyed by message id or command and option) only when someone offers a language. Raised 2026-10-26; after the current Now/Next.
