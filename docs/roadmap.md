# Roadmap

What is planned, in the order agreed with the maintainer, and what waits on a decision. The design documents hold the details of each plan ([docs/design/README.md](design/README.md) lists them with their status); this page holds the order.

Keep it current:

- Read it before starting new work, and before proposing any.
- Update it in the same PR that starts, finishes or drops an item. Move a finished item to "Done lately" with its PRs.
- Add an item when the maintainer agrees to a plan, or asks for something that will not be done at once. An idea nobody agreed to goes under "Not decided".

## Next, in this order

1. Every pitfall stated as a problem, with its level and its range, once the thinned analyzer gives note nodes ([design/note-levels.md](design/note-levels.md), "The bridge"): the views then read the level from the node, not from the note's mark (`noteLevel`, `splitNote`). Today only the pitfalls of src/pitfalls.ts and src/wordfacts.ts are problems; the other notes found on a node already carry its range (`LineExplanation.anchors`, for the part hover). Decided with the hover ([design/hover.md](design/hover.md)); the other notes stay out of the diagnostics until then.
2. Lists as the manual reads them (3.2.4): a list is pipelines separated by `;`, `&`, `&&` or `||`, where `&&` and `||` bind tighter than `;` and `&`. Today only an `&&`/`||` group is a node, labelled 'Command list' (the manual calls it an AND or OR list), and `a; b & c && d` gets no list node at all; Reading's tree leaves out `;`. Show the whole list with its four operators and their precedence (what `&` applies to), in Meaning and Reading. Raised by the maintainer 2026-10-26.
3. Audit Reading against the Bash Reference Manual, section by section (chapter 3 first): every construct Reading shows is named and grouped as the manual does, and every operator and reserved word appears in the tree. Findings fixed as explanation bugs, with tests against bash or bash-ast. Raised by the maintainer 2026-10-26.
4. Trust per position instead of per script: a `source`, `eval` or `$cmd` makes variables untrusted only on the paths after it, not in the whole file. Shared with conditions and dead code. Design: [design/trust-per-position.md](design/trust-per-position.md) (planned). Its step 0 fixes wrong values and dead code of today's model found on the way (`-v` of a name not known, reads of a nameref whose target is not known, `${x@P}`, a bare `declare n` from the environment read as arithmetic, `compgen -W`, `fc -s`, recursive calls, `enable -n exit`). Measured again with a prototype, the gain is small (34 to 45 values on 358 corpus files; every function body is lost after a taint in the main flow); the maintainer decides whether steps 1–4 keep this place (section 10 there).
5. Values of top-level constants inside functions (assigned once before any call, no other writer).
6. The basis of an explanation, as data, after the analyzer is thinned: an explanation that rests on bash's behaviour rather than the manual gets a chip ("Not in the manual · checked with bash 5.2", or "Differs from the manual"), and a folded "Try it in your terminal" with a command and its output, taken from the probe that checks it in CI (look A of the prototype on branch `proto/basis`). A setting turns the chips and the try-its off. Other kinds of basis (another tool's spec, convention) are data only for now.
7. bash 5.3, steps 3–7 of [design/bash-versions.md](design/bash-versions.md): the walk of `${ }`, version-gated options, the variables and shell options of 5.3, the POSIX-mode and `test` differences, the 5.3 manual.
8. Run-based oracles, steps 2–10 of [design/oracles.md](design/oracles.md): argv capture, checking suggestions in bash, the normal-forms audit.
9. Pipeline examples: show the shape of the input each stage reads (item 3 of the external review of October 2026).
10. bats, what [design/bats.md](design/bats.md) lists as not done: a model per test (its own process, `set -e`), hooks, bats-assert, tags.
11. Dead code faded in the editor: a `DiagnosticTag.Unnecessary` hint on a statement that never runs (`shellState(...).dead(n)`), with its message in the catalog and on every surface ([design/highlighting.md](design/highlighting.md)).
12. Values of a whole word (`"$dir/$f"`), arrays, and per-call values in functions: after items 4 and 5; the corpus shows little gain ([design/expansion-values.md](design/expansion-values.md), section 6).
13. The leftovers of the small gaps (A3): the readers of arguments that have no shell at hand (`argWord` in src/semantics/env.ts, effects.ts, vars.ts, src/idioms.ts, src/semanticFacts.ts) count the words of a brace expansion in every shell; and a BSD letter of ps with a value takes the rest of its word (`ps opid,comm`, `ps Uroot`), which the argument interpreter reads as the next word.

## Not decided

- Read a file given to `source` when it is in the workspace (a static path, or one next to the script), as the walk reads a static `eval` string. The first cause of blindness in 72 of 136 corpus files; more gain than trust per position, also inside functions ([design/trust-per-position.md](design/trust-per-position.md), section 9). Raised 2026-10-26.
- Web page follow-ups of opening and saving files (#358): "Save as…" for an opened file; a CRLF→LF conversion (the `crlf` warning says to convert, and the page has no way to); the file name in share links.
- Variable kinds: say what a variable name is where it is used, as the name kinds do for commands: a shell variable, an exported (environment) variable that child processes see, a special parameter (`$?`, `$@`), a function's local, or one bash sets itself (`RANDOM`, `SECONDS`). The model already has the attributes (`shellState`). It answers the same question as `sudo echo`: what a child process sees.
- Makefile recipes: make execs simple lines directly; the badge should say program, run by make. (GNU make runs a recipe line with no shell syntax without a shell: `echo -e x` execs `/bin/echo`, which prints `-e x`; the badge says builtin.)
- `which` against `type` and `command -v`: a sentence saying that `which` looks only for programs on PATH, while `type` and `command -v` also find builtins, functions and aliases, so their answers can differ.
- A third language. Today ja/en pairs sit in about 100 files (75% in src/dict specs, the message catalog, ~2,200 inline pairs in code), the language list is repeated in ~10 places, and about 12 copies of `lang === 'ja' ? ja : en` would show any new language as English without a warning. Proposed cheap steps first (one `LANGS` list that the settings enum, CLI, web menu and build derive from; keyed `Text` records and one `pick` with an English fallback instead of positional `(ja, en)`; inline texts moved into per-module catalogs; a CONTRIBUTING section listing what to touch), and per-language overlay files (`locales/<lang>/…`, keyed by message id or command and option) only when someone offers a language. Raised 2026-10-26; after the current Now/Next.

## Done lately

- Small gaps of the specs and the models (A3): `ps u1` reads the number after BSD letters as PIDs (or the value of the last letter, `ps t1`), `tar vf a.tar` is letters (`oldStyle.numbers`, `tar`'s `oldStyle` without `needs`); the word model applies brace expansion by shell, as `src/dialect.ts` says (none in dash, POSIX sh, ash, yash; no ranges in mksh), so `echo {a,b}` in a dash script is a plain word, with no example, and the redirection target reads the model (src/semantics/brace.ts; [design/semantics.md](design/semantics.md)).
- The shebang line says it takes effect only when the file is run as a program (execve(2), "Interpreter scripts"; bash itself where the kernel does not), and is a comment to `bash script` and `source`; it says the shell Bash Explainer reads the script as. A manual page is a new kind of reference (src/references.ts: `execve(2)`, linked in the panel, the hover, Markdown and the web hover's allow-list). The shebang is its own kind, `shebang`, in a command's colour in the panel and the web editor, a role of the theme palettes, and a semantic token type with `superType: comment`.
