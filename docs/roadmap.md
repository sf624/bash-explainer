# Roadmap

What is planned, in the order agreed with the maintainer, and what waits on a decision. The design documents hold the details of each plan ([docs/design/README.md](design/README.md) lists them with their status); this page holds the order.

Keep it current:

- Read it before starting new work, and before proposing any.
- Update it in the same PR that starts, finishes or drops an item. Move a finished item to "Done lately" with its PRs.
- Add an item when the maintainer agrees to a plan, or asks for something that will not be done at once. An idea nobody agreed to goes under "Not decided".

## Now

- Pipeline examples: show the shape of the input each stage reads (item 3 of the external review of October 2026). First step in review: made-up output in the real layout for `ps`, `ls`, `df -h`, `who`, `env` (`CommandSpec.layouts`), and input labels that name the command a pipe brings them from; each section marks what the next stage reads (grep's and sed's matches, awk's and cut's fields, sort's keys), and a wide table starts scrolled to its first mark. Waits on the maintainer's look at the screenshots.

## Next, in this order

1. Trust as a strict allow-list: the trust scan looks every construct up in a table (node types, builtins and their options, `set` and `shopt` options, bash's own variables, expansion operators), and one it does not know makes the script trust nothing, instead of being taken to change nothing. Each row the model follows names its tests. It closes the four findings of the #382 review that #387 leaves open (`${n:=0}`, `n="$n"` and `+=` read as arithmetic, `${x@P}` built with `+=`, `set -H`, `case … ;;&`), twelve more holes found for the design (`compat31`, `compat42`/`BASH_COMPAT`, `FUNCNEST`, `BASH_ALIASES`, `set -C`, `set -k`, redirections that fail, `jobs -x`, shebang options, values given to `bash -c`, environment values copied into arithmetic, `{a[i]}>`). Its first draft, measured on top of #387, cost no value, decision or dead mark on the corpus and on 802 real scripts; the walk changes the review added (redirections that may fail above all) are measured in its step 3. Design: [design/trust-allow-list.md](design/trust-allow-list.md) (in progress: steps 1 to 3 done, the builtins' options in the specs, the table with today's effects, and the walk changes with copies of IFS; step 4, the default flip, waits on the maintainer). Placed right after item 1, which is in progress (#386). Proposed 2026-10-26.
2. Audit Reading against the Bash Reference Manual, section by section (chapter 3 first): every construct Reading shows is named and grouped as the manual does, and every operator and reserved word appears in the tree. Findings fixed as explanation bugs, with tests against bash or bash-ast. Raised by the maintainer 2026-10-26.
3. Values of top-level constants inside functions (assigned once before any call, no other writer).
4. The basis of an explanation, as data, after the analyzer is thinned: an explanation that rests on bash's behaviour rather than the manual gets a chip ("Not in the manual · checked with bash 5.2", or "Differs from the manual"), and a folded "Try it in your terminal" with a command and its output, taken from the probe that checks it in CI (look A of the prototype on branch `proto/basis`). A setting turns the chips and the try-its off. Other kinds of basis (another tool's spec, convention) are data only for now.
5. bash 5.3, step 3 of [design/bash-versions.md](design/bash-versions.md), the walk of `${ }` (the substitution walk moved out of src/semantics/walk/walker.ts first), and the POSIX-mode rows of step 6.
6. Run-based oracles, steps 2–10 of [design/oracles.md](design/oracles.md): argv capture, checking suggestions in bash, the normal-forms audit.
7. Dead code faded in the editor: a `DiagnosticTag.Unnecessary` hint on a statement that never runs (`shellState(...).dead(n)`), with its message in the catalog and on every surface ([design/highlighting.md](design/highlighting.md)).
8. Values of a whole word (`"$dir/$f"`), arrays, and per-call values in functions: after item 3 and trust per position (item 10); the corpus shows little gain ([design/expansion-values.md](design/expansion-values.md), section 6).
9. The leftovers of the small gaps (A3): the readers of arguments that have no shell at hand (`argWord` in src/semantics/env.ts, effects.ts, vars.ts, src/idioms.ts, src/semanticFacts.ts) count the words of a brace expansion in every shell; and a BSD letter of ps with a value takes the rest of its word (`ps opid,comm`, `ps Uroot`), which the argument interpreter reads as the next word.
10. Trust per position instead of per script: a `source`, `eval` or `$cmd` makes variables untrusted only on the paths after it, not in the whole file. Shared with conditions and dead code. Design: [design/trust-per-position.md](design/trust-per-position.md) (deferred; step 0 done). Its step 0, done (#382), fixed wrong values and dead code of today's model found on the way (`-v` of a name not known, reads of a nameref whose target is not known, `${x@P}`, a bare `declare n` from the environment read as arithmetic, `compgen -W`, `fc -s`, recursive calls, `enable -n exit`). Steps 1–4 deferred: the measured gain is small (34 → 45 values on 358 real scripts). (Measured with a prototype: every function body is lost after a taint in the main flow; section 10 there.) Decided by the maintainer 2026-10-26.

## Waiting on the maintainer

- Trust as a strict allow-list, step 4: flip the default (a construct with no row trusts nothing, and the rows marked "new" take their effect). Steps 1 to 3 are in review ([design/trust-allow-list.md](design/trust-allow-list.md), section 6).

## Not decided

- Read a file given to `source` when it is in the workspace (a static path, or one next to the script), as the walk reads a static `eval` string. The first cause of blindness in 72 of 136 corpus files; more gain than trust per position, also inside functions ([design/trust-per-position.md](design/trust-per-position.md), section 9). Raised 2026-10-26.
- Web page follow-ups of opening and saving files (#358): "Save as…" for an opened file; a CRLF→LF conversion (the `crlf` warning says to convert, and the page has no way to); the file name in share links.
- Variable kinds: say what a variable name is where it is used, as the name kinds do for commands: a shell variable, an exported (environment) variable that child processes see, a special parameter (`$?`, `$@`), a function's local, or one bash sets itself (`RANDOM`, `SECONDS`). The model already has the attributes (`shellState`). It answers the same question as `sudo echo`: what a child process sees.
- Makefile recipes: make execs simple lines directly; the badge should say program, run by make. (GNU make runs a recipe line with no shell syntax without a shell: `echo -e x` execs `/bin/echo`, which prints `-e x`; the badge says builtin.)
- `which` against `type` and `command -v`: a sentence saying that `which` looks only for programs on PATH, while `type` and `command -v` also find builtins, functions and aliases, so their answers can differ.
- A third language. Today ja/en pairs sit in about 100 files (75% in src/dict specs, the message catalog, ~2,200 inline pairs in code), the language list is repeated in ~10 places, and about 12 copies of `lang === 'ja' ? ja : en` would show any new language as English without a warning. Proposed cheap steps first (one `LANGS` list that the settings enum, CLI, web menu and build derive from; keyed `Text` records and one `pick` with an English fallback instead of positional `(ja, en)`; inline texts moved into per-module catalogs; a CONTRIBUTING section listing what to touch), and per-language overlay files (`locales/<lang>/…`, keyed by message id or command and option) only when someone offers a language. Raised 2026-10-26; after the current Now/Next.

## Done lately

- Lists as the manual reads them (3.2.4): the commands joined by `;` and `&` are one list in Meaning and Reading, AND and OR lists (`&&`, `||`) are parts of it, nested from the left, and each `;` and `&` says what it applies to; Reading shows every `;`. The tree keeps a body's statements as they were; `commandLists` (src/syntax/tree.ts) reads them as lists, checked against bash-ast and bash (test/lists.test.ts).
- Every warning and caveat the explanations say is a problem, with its level, its range and its code, on every surface (VS Code, the Language Server, the web page, `--check`, SARIF, the Action), also in the shell code of host files; a plain fact never is. The notes are data with their level (`LineExplanation.noteInfo`), which the views read instead of the mark (`noteLevel` and `splitNote` are gone) (#365, #366; [design/note-levels.md](design/note-levels.md), "Notes as data", "Notes as problems").
- bats: the model per test and the hooks (#381), tags and `# @test` functions (#384), and the helpers of bats-support, bats-assert and bats-file as specs (#374). What [design/bats.md](design/bats.md) still lists as not done (the code outside the tests, the test names in the C locale) is small and waits for a user who needs it.
- The example of a brace expansion shows the words as chips in a row (a list for a screen reader; code spans on one line in Markdown, the CLI and the hover), cut after 11 with the count, and what `echo` or `printf` prints with them; the examples of `printf` and of pipelines run the expanded words (#371).
- Small gaps of the specs and the models (A3): `ps u1` reads the number after BSD letters as PIDs (or the value of the last letter, `ps t1`), `tar vf a.tar` is letters (`oldStyle.numbers`, `tar`'s `oldStyle` without `needs`); the word model applies brace expansion by shell, as `src/dialect.ts` says (none in dash, POSIX sh, ash, yash; no ranges in mksh), so `echo {a,b}` in a dash script is a plain word, with no example, and the redirection target reads the model (src/semantics/brace.ts; [design/semantics.md](design/semantics.md)).
- The shebang line says it takes effect only when the file is run as a program (execve(2), "Interpreter scripts"; bash itself where the kernel does not), and is a comment to `bash script` and `source`; it says the shell Bash Explainer reads the script as. A manual page is a new kind of reference (src/references.ts: `execve(2)`, linked in the panel, the hover, Markdown and the web hover's allow-list). The shebang is its own kind, `shebang`, in a command's colour in the panel and the web editor, a role of the theme palettes, and a semantic token type with `superType: comment`. A byte order mark before `#!` is a pitfall ([design/highlighting.md](design/highlighting.md)).
- bash 5.3, step 6 of [design/bash-versions.md](design/bash-versions.md) for `test`: a group of up to four words read as each release reads it, checked with generated lists in both; the models decide only what both read alike.
- bash 5.3, step 5 of [design/bash-versions.md](design/bash-versions.md): `GLOBSORT`, `BASH_TRAPSIG`, `BASH_MONOSECONDS` (plain variables in 5.2 mode), and the `shopt` options `array_expand_once` and `bash_source_fullpath` (with `laterOption` in 5.2 mode).
- bash 5.3, step 4 of [design/bash-versions.md](design/bash-versions.md): `source -p`, `compgen -V`, `trap -P` and `read -E` in the specs (`OptionSpec.since`), with the issue `laterOption` in 5.2 mode.
- bash 5.3, step 7 of [design/bash-versions.md](design/bash-versions.md): test/manual.test.ts checks the manual table against the 5.3 bashref.texi too, in CI's `bash53` job.
- bash 5.3, step 2 of [design/bash-versions.md](design/bash-versions.md): `printf` formats as each release reads them (`%#q`, `%ls`, `%S`, `%C`), and in both, `%ld`, `%Q`, byte counts and what `%q` quotes; `env printf` as coreutils reads it.
