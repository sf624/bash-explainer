## Build and run

```sh
npm install
npm run build      # bundle into dist/
npm test           # type check + unit tests
npm run coverage   # unit tests with coverage (report in coverage/index.html)
npm run package    # build a .vsix
npx tsx scripts/extract-snippets.ts   # after changing the scripts in the tests: rewrite test/fixtures/snippets.json, the inputs of the syntax tests and the fuzz (CI runs it with --check)
npx tsx scripts/argv-corpus.ts   # before a release, or after changing the word model: the argv check of test/argv.test.ts over every snippet and 200 fuzz inputs (CI runs a sample)
npx tsx scripts/normal-forms-sweep.ts --count 1000   # after changing a normalizer (quoting, command names, options): the generated forms of test/normal-forms-gen.test.ts, many more of them (CI runs a sample); --seed N for other forms, --missed to list the missed matches
npx tsx scripts/capture-web.ts --out DIR --name after   # screenshots of the web page (390, 640 and 1280 px, English and Japanese, light; --themes light,dark) for a visual PR; --name before on main, for the pair
npm run test:integration   # run the extension in VS Code (downloaded into .vscode-test/)
npm run test:integration:web   # …and in VS Code for the Web (needs `npx playwright install chromium`)
```

- Press `F5` in VS Code to launch an Extension Development Host with `test/fixtures/playground.sh` open (a gitignored copy of `sample.sh`, the tour of every feature, made when it is missing; edit it freely), with the panel beside it (`.vscode/playground.code-workspace` turns on `bashExplainer.panel.autoOpen`). F5 first runs `npm install`, so `node_modules` follows `package-lock.json` after a pull.
- `npm run build:web` builds the web version into `site/` (`-- --channel=next` builds the development version shown at `/next/`, with its banner); `python3 -m http.server -d site` serves it at <http://localhost:8000/>.
- To try the command-line tool from this repository, `npm run build:cli`, then `node cli/dist/cli.js <file>` (or `npx --package=./cli bash-explainer <file>`). A bare `npx bash-explainer` does not work here: the extension's own `package.json` is also named `bash-explainer`, so npx takes this project for the package.
- `npx tsx test/dump.ts <file> [en|ja] [line]` prints the explanation of every line of a file.

## Tests

- Tests that compare with real tools use the shells on `PATH` or in `$BASH_EXPLAINER_SHELLS`, and the yq releases in `$BASH_EXPLAINER_YQ`; the yq examples use mikefarah/yq from `$BASH_EXPLAINER_YQ4` (a path to the program), or a mikefarah `yq` on `PATH` (CI installs v4.54.1, MIT, checked by its SHA-256); missing ones are skipped. `test/bash-ast.test.ts` compares the syntax tree with bash's own parser through [bash-ast](https://github.com/cv/bash-ast) (GPL: used only as an external program, never a dependency or part of a bundle), found at `$BASH_AST` or on `PATH`; without it the test is skipped. CI runs it with the pinned release v0.3.3 (`bash-ast-v0.3.3-x86_64-unknown-linux-gnu.tar.gz` from <https://github.com/cv/bash-ast/releases/tag/v0.3.3>; the known differences are those of this version), downloaded on each run, checked by its SHA-256 and never stored or redistributed; set `BASH_EXPLAINER_BASH_AST=1` to fail instead of skipping when it cannot be run. `test/host-shells.test.ts` compares the scripts we read in YAML block scalars with those PyYAML loads (`python3 -c 'import yaml'`); without PyYAML it is skipped, and `BASH_EXPLAINER_PYYAML=1` (set in CI) makes that fail. To run only this test: `npx mocha --no-config --node-option import=tsx test/bash-ast.test.ts` (`--spec` would add to the whole suite). Its known differences are listed, with reasons, in `test/fixtures/bash-ast-known.json`; the test fails on a new difference and on an entry that no longer applies. `test/command-tokens.test.ts` uses it the same way: each token of the explanations lies in exactly one innermost command of our tree, crosses no command's boundary, and that command is one of bash-ast's, in the script or in the text of a substitution (see docs/design/syntax-tree.md); its known findings and the counts it pins are in `test/fixtures/command-tokens-known.json`. `test/bash53.test.ts` checks what we say of bash 5.3's constructs (`${ cmd; }`, `${| cmd; }`) with a real bash 5.3, found at `$BASH_EXPLAINER_BASH53` (a path; skipped without it, and `BASH_EXPLAINER_BASH53_REQUIRED=1` makes that fail), and with the bash 5.2 on `PATH`. CI builds bash 5.3 from the release tarball, checked by its SHA-256 (`./configure --without-bash-malloc && make`), in a job of its own; bash is GPL, so it is only run as a separate program and never stored or redistributed. `test/python-lexer.test.ts` holds the Python host's lexer and the values of its string literals against the reference Python's `tokenize` and `ast`, on the files of `test/fixtures/python/`: the release of `PYTHON_REFERENCE` (src/hosts/pylex.ts), found at `$BASH_EXPLAINER_PYTHON` (a path) or as `python3` of that release; without it the comparison is skipped, and `BASH_EXPLAINER_PYTHON_REQUIRED=1` makes that fail. CI installs it with actions/setup-python, in a job of its own. bazel (Apache-2.0, but a JVM program that fetches its rules from the network) is not run by the tests: `test/parsers-real.test.ts` reads what bazel read of its rows from `test/fixtures/oracles/bazel.json` (and `test/bazel-patterns.test.ts` the targets it took of target patterns), which `scripts/record-bazel.ts` records with the bazel or bazelisk of `$BAZEL` in a copy of `test/fixtures/bazel` (the release of its `.bazelversion`; `--check` fails if bazel no longer reads a row so). Record again after adding a row, and read the facts it wrote. The web page test needs Chromium (`npx playwright-core install --with-deps chromium-headless-shell`). Mocha runs the test files in parallel (`.mocharc.cjs`: three workers, on Node.js 20 or later; each file in one worker, a worker runs its files one after another); parallel mode ignores `.only` and a `this.timeout()` outside a `describe`, so for one file, or to debug, use `npx mocha --no-parallel --spec test/x.test.ts` (or `--no-config` as above). Every web test file builds and serves its own copy of the page, and closes it after the file.
- CI runs the unit tests in four shards per Node.js version, each on a runner of its own: [scripts/test-shards.cjs](scripts/test-shards.cjs) splits the files by the times measured in `scripts/test-timings.json` (a new file counts as the median), and `test/shards.test.ts` checks that each file is in exactly one shard. `MOCHA_SHARD=2/4 npx mocha` runs one shard; When the shards' jobs drift apart, measure the times again in CI with `node scripts/test-shards.cjs --measure` (its header says how). The job `Test (Node.js …)` passes when the type checks and every shard of its Node.js version passed, and the package builds on that version; on Node.js 24 it also merges the shards' coverage.
- The web page's own checks (docs/design/chrome-redesign.md, C0): `test/ja-style.test.ts` also reads the Japanese in `web/` (`web/*.ts` and `web/index.html`); `test/file-length.test.ts` keeps `web/*.ts` under 1,000 lines too; `test/web-css.test.ts` runs stylelint (MIT, a devDependency; `.stylelintrc.json`) over `web/*.css`, so that a selector is written once per file and a property once per block; `test/web-hit-areas.test.ts` measures the hit area of every control of the page (`elementFromPoint` from its centre outwards) at 390, 640 and 1280 px in both languages, and wants at least 44x44 px on a phone and 24x24 px beside others (a dimension under the bar is what is gated), except the smaller controls listed in `test/fixtures/hit-areas.json`, a list that may only shrink (remove an entry when its control meets the bar; never add one for a new control). The web tests choose the shell and open the Problems list through the helpers of `test/support/site.ts` (`setShell`, `openProblems`), so that moving a control changes a helper, not many tests.
- `npx tsx scripts/capture-web.ts --out DIR [--name before|after] [--widths 390,640,1280] [--langs en,ja] [--themes light,dark] [--states page,menu,settings,kind,tip] [--script FILE] [--phone-scale 1.3]` builds the web page, serves it on 127.0.0.1 and takes its screenshots (`DIR/NAME-WIDTH-LANG-THEME-STATE.png`; the phone's first-run tip of the read-mode switch is closed first, and is a state of its own, `tip`); every visual PR attaches the before and after sets, and its author looks at them and measures before pushing. It uses Playwright's browser (`npx playwright-core install chromium`; Playwright's own variables such as `PLAYWRIGHT_BROWSERS_PATH` apply) and draws Japanese with whatever fonts the machine has: to get the CJK fonts of CI (IPAGothic, WenQuanYi), point `FONTCONFIG_FILE` at a fontconfig file that lists them (`apt-get download fonts-ipafont-gothic fonts-wqy-zenhei`, `dpkg -x` into a directory of your own). Run it under a memory cap (`systemd-run --user --scope -p MemoryMax=3G -p MemorySwapMax=0 -p TasksMax=500 …`) and, where heavy runs are queued, in that queue.
- `npx tsx test/snapshot.ts <output file>` writes the full explanation of every line of the test corpus (fixtures, host fixtures, snippets), in Japanese and English, as JSON lines, with a fixed clock and time zone. For refactoring: run it on main and on the branch, and compare with `git diff --no-index --stat` (see [docs/design/analyzer.md](docs/design/analyzer.md)). `test/file-length.test.ts` keeps files of `src/` under 1,000 lines (the listed exceptions have ceilings that may only go down, in `test/fixtures/file-length.json`), and `test/explain-imports.test.ts` keeps `src/explain/` free of import cycles and of comparisons with command names.

## Coverage

- CI measures the coverage of the unit tests with every tool installed (the Node.js 24 job): the run's summary lists the least covered files, and the `coverage` artifact holds the HTML report. Measured locally, it is lower when tools are missing, as their tests are skipped; use Node.js 24 as CI does, since older versions count methods that never ran as covered. `npm run coverage` runs in UTC, as CI does, since some branches depend on the time zone. The reports leave out the code that tsx adds when it compiles the sources for the tests (its helpers, the getters of exports), which maps to places no test can run ([scripts/coverage-report.mjs](scripts/coverage-report.mjs)).
- Every line of `src/` must run in a unit test, and every branch must be taken, or CI fails (`npm run coverage:check`). Every file is at 100%, so [coverage-floors.json](coverage-floors.json) is empty. A file listed there would keep a floor, its share then, which must not go down; after adding tests, `node scripts/coverage-check.mjs --update` raises the floors and drops the files that reach 100%. A branch no test can take is removed, or, when it guards against a bug elsewhere, marked with `/* c8 ignore next */` and a comment saying why. The VS Code side (`extension.ts`, `service.ts`, `ui/` except the renderers) is left to the integration tests. The coverage badge at the top of the README is static; it stays true because CI fails below 100%.

## Dependencies

- After changing dependencies, run `npm run notices` to regenerate [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md) from what the builds include; a test fails while it is out of date, or if something under a license not yet reviewed gets in.
- A weekly workflow ([unbash-release.yml](.github/workflows/unbash-release.yml)) opens an issue when a newer unbash (the parser, pinned exactly in `package.json`) is on npm, with the upgrade checklist; Dependabot's monthly npm run proposes the same bump as a PR.

## Writing explanations

- Japanese text follows [docs/japanese-style.md](docs/japanese-style.md) (in Japanese); a test checks it.
- To add a command, add an entry to [`src/dict/commands.ts`](src/dict/commands.ts): `cmd(japanese, english, [options…], { positional: […] })`. Write the descriptions in your own words: do not copy them from man pages, `--help` output or other documentation, whose licenses (often the GPL or the GFDL) differ from this project's.

## User documentation

- The user documentation is [README.md](README.md) and [README.ja.md](README.ja.md), which the Marketplace, Open VSX and GitHub show, and the user guide in [docs/guide/](docs/guide/README.md): English pages in `docs/guide/`, Japanese pages under the same names in `docs/guide/ja/`. The two READMEs have the same sections, and so have the two pages of each pair. Keep the READMEs short: a new detail goes into a guide page.
- The guide is plain Markdown (no HTML beyond what the READMEs already use), so that a documentation site can be built from these files later.
- `test/docs-links.test.ts` checks that every relative link and anchor of the READMEs, this file and the guide resolves, and that every guide page has its pair in the other language; `test/ja-style.test.ts` reads README.ja.md and `docs/guide/ja/` too. The package pages show the README pinned to the release's tag (`scripts/readme-pins.ts`), so a guide page the README links must be in the repository at that tag, and an image the README of a release names stays at its path ([docs/publishing.md](docs/publishing.md)).

## Changelog and releases

- `CHANGELOG.md` is for users: it is the GitHub Release's notes and the Marketplace's Changelog tab. Add entries under `## Unreleased`, in `### New`, `### Changed` or `### Fixed`: one bullet per change users can see, in one or two short sentences that say what they see now. Write "Before, …" only when the behaviour changes in a way users will notice, not for every fix. Leave out tests, CI, refactors and internal design. Each version ends with an `[All changes]` link to GitHub's compare view of the previous and this tag (`compare/vPREV...vX.Y.Z`).
- Fine-grained examples and the earlier behaviour go into `docs/changes/<version>.md`, linked from the version's section in `CHANGELOG.md` (for unreleased work, `docs/changes/unreleased.md`, linked from `## Unreleased`). When a change is a fix of a kind already listed, add a few words or an example to the details file; do not grow the bullet.
- To release, bump `version` in `package.json` and `cli/package.json`, rename `## Unreleased` in `CHANGELOG.md` to the version, rename `docs/changes/unreleased.md` to `docs/changes/<version>.md` (and fix its link in the section to `https://github.com/sf624/bash-explainer/blob/v<version>/docs/changes/<version>.md`), and push a tag `v<version>`. The [Release workflow](.github/workflows/release.yml) takes the version's section of `CHANGELOG.md` as the release notes, so keep the section short and the details link in it. It checks that the Test workflow passed on the tagged commit, packages it, waits for approval in the `release` environment, then publishes to the VS Code Marketplace, Open VSX and npm, creates a GitHub Release, moves the `v0` tag the GitHub Action is used by, and updates the web version; see [docs/publishing.md](docs/publishing.md) for the steps and the one-time setup. The package pages show the README of their version: the packages are pinned to the tag (`npm run package`, `scripts/build-cli.ts --tag`), and the release checks it. Run by hand (Actions, Release, Run workflow), the Release workflow is a dry run: it does the checks and packages the extension, and publishes nothing.
