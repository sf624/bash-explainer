# Changelog

## Unreleased

- More idioms get a note, with the one thing people get wrong: `while getopts` and `shift $((OPTIND-1))`, `getopt` with `eval set -- "$args"`, the `while [ $# -gt 0 ]` loop over the arguments, `read -d ''`, `find -print0`, `xargs -0`, `until`, `mapfile`/`readarray`, `[ -e "$f" ] || continue` after a glob, and a `read -p '… [y/N] '` question. `while getopt` (no `s`) says that `getopt` is another program. Before, these had no note.
- The example of `xargs -0 -n 1 -I{} rm -f {}` runs `rm -f` once for each NUL-separated name. Before, it showed one run with all three names joined by NUL bytes. The same holds for `-d` with `-I`.
- The options of `git` before the subcommand are read one word each, as git reads them: `git -pP log` and `git -C. log` are unknown options, as git says ("unknown option: -pP"). Before, `-pP` was `-p` and `-P`, and `-C.` was `-C` with the value `.`. The options of a subcommand still cluster (`git commit -am x`).
- In `ip - 3 link`, the lone `-` is the option `-loops`, as iproute2 reads it (it takes the first option the word starts). Before, `-` was a plain argument.
- A long option that is the start of several options, as `timeout --v`, `env --ig` and `xargs --max`, is shown as ambiguous, with the options it could be (`--verbose`, `--version`), and says that the tool refuses it. Before, it was "Option (not in the dictionary)".
- `env -S'-i A=1' printenv A` and `env -S-i A=1 cmd` read the words after the `-S` string as env reads them when the string holds only options and assignments: `A=1` is a variable and `cmd` the command. Before, they were arguments of a command "made from the string". With a command in the string (`env -S'-i A=1 printenv' x`), `x` is still its argument.
- In `ps`, a bare number is a process ID, and it ends the line: procps reads every word after it as a process ID, and `ps -o pid= 1 u` and `ps 1 -e` fail with "process ID list syntax error". The explanation marks those words as not allowed. Before, `1` was a plain word, and `u` and `-e` were read as options.
- The value of an option written in the same word as quotes, as in `dpkg-query -Wf='${Package}'` and `tar -C'/tmp' -xf a.tar`, is shown without the closing quote (`${Package}`, `/tmp`), and its mark ends before the quote. This covers values written with plain quotes; a value with escapes or `$'…'` still shows the raw text. Before, the label kept the quote (`${Package}'`).
- `sh` knows `-s`, `-i`, `-l`, `-n`, `-v`, `-a`, `-C`, `-f`, `-b`, `-m` and `-p`, as dash and `bash --posix` do. In `sh -s a b` and `sh -i`, they are options. Before, they were "Option (not in the dictionary)".
- `jobs -x echo %1` explains `echo %1` as a command, with its own words, as `-x` runs it. Before, `echo` and `%1` were job specs.
- In `shopt -o errexit`, `shopt -so pipefail` and the like, the names are explained as `set -o` options (before: plain words with the text of a `shopt` name).
- `pushd +1`, `pushd -1`, `popd -2` and `dirs +0` say which entry of the directory stack they mean, counted from the left (`+`) or the right (`-`) of what `dirs` prints. Before, `+1` was a plain argument and `-2` an unknown option.
- `kill -s9 1` and `kill -nTERM 1` say that bash refuses the signal spec (`s9`, `nTERM`): a name may be attached to `-s` and a number to `-n`, nothing else. Before, they were read as `-s 9` and `-n TERM`. After a signal was given, as in `kill -9 -s9 1`, `-s9` is a process ID. In `kill -l -15`, `-l -9`, `-l -KILL`, `-l -0`, `-l -s HUP` and `-l -sHUP`, the signal word is said to send nothing, as `-l` only lists the signals. Before, each was "Send signal …".
- A redirection after the closing word of a loop, `if`, `case`, `{ }`, `( )` or function body is explained on the first line too, as a child of the header: `while read -r line; do … done < input.txt` says that `< input.txt` is the stdin of the whole loop, so `read` reads from it. Before, only the `done` line said anything about it. `while read … done < file` and `done < <(command)` also get an idiom note on reading line by line, with the last line without a newline that `read` skips.
- Options written with quotes or an expansion are read as options. `ls "-l"`, `tar "xf" a.tar`, `dpkg-query -W -f='${Package}'`, `ls -$opts`, `ls -l$x`, `head -$n` and `kill -$sig` show the option (and its value); `-$opts` says the letters are known only at run time. Before, each was a plain argument: a file, a package name, or a PID.
- The words of a command run by another one are read as that command reads them. In `ssh host ls -l`, `-l` is the remote `ls`'s option (before: ssh's login name). In `flock /tmp/l -n true`, `-n` is the command flock runs, as flock reads it (before: flock's `-n`). In `bash -ex script.sh -x`, the last `-x` is `$1` of the script (before: an option of bash). `bash +x s.sh` turns `-x` off and runs `s.sh` (before: `+x` was the script). In `sh -s -- --prefix x`, `--prefix` is `$1` (before: the script to run). In `eval set -- "$OPTS"`, the `--` goes to `set` (before: the end of eval's options). The pitfall of `find -ok` and `-execdir` names that option (before: always `-exec`).
- More words of builtins and tools are read right. In `kill -9 -1` and `kill -s TERM -1`, `-1` is a process group (before: signal 1). `let -1+2` is an expression (before: unknown options). `nice --5` is an adjustment of -5 (before: an unknown option). `jq --arg=x` is an unknown option, as jq says (before: `--arg` with a value). In `chmod --reference=r u+x`, `u+x` is a file (before: also explained as a mode). `su -` says "as a login shell (fresh environment)", the text of `-l`.
- The pitfalls of a command run by another one follow from how it is run. `exec f`, `npx f`, `uv run f`, `poetry run f` and `systemd-cat f` say that a function of the script cannot run, as `sudo f` does, and `exec cd /x` that a builtin cannot (before: nothing; bash says `exec: cd: not found`). So do `env disown`, `xargs :` and the other builtins that no program is named after (before: only `cd`, `export` and a fixed list). `docker run img f`, `docker exec`, `docker compose run|exec`, `podman run` and `kubectl exec pod -- f` say that a function from this script is not available in the container (before: nothing). `bash -c 'f'`, `sh -c 'f'` and `flock FILE -c 'f'` say that the new shell does not have the function, unless the script exports it with `export -f f` (before: only `su -c` said so).
- `command -v git` and `command -V ls cd` take their words as names to look up (before: `git` was a command that runs). `timeout` knows `--preserve-status`, `--foreground` and `-v`, and `timeout` and `nice` accept a long option shortened to a unique prefix, as they do: in `timeout --sig KILL 5 cmd`, `KILL` is the signal and `5` the time limit (before: `--sig` was unknown, `KILL` the time limit and `5` the command).
- A word that becomes several words says what each one is. `cp config.yml{,.bak}` expands to `config.yml` (source) and `config.yml.bak` (destination). When the number of words is not known, both cases are given: in `cp *.txt dir`, `dir` is the destination when `*.txt` is one file, and the destination directory when it is more. Before, only the first role was given.
- `exit -1`, `return -1`, `shift -1`, `break -1` and `continue -1` take `-1` as their number, as bash does (`exit -1` exits with 255). Before, `-1` was an unknown option. In `kill -sigint` and `kill -stop`, a lowercase `-s` and a letter are `-s` with a signal name (bash reads `igint`, which is no signal). Before, they were the signals `INT` and `STOP`.
- `ps` reads its BSD letters in any place, as procps does: in `ps -p 1 u`, `u` is the user-oriented format, and in `ps -p 1 o pid,comm`, `pid,comm` the columns of `o`. Before, only the first word could hold them, and `u` was a plain argument. `tar --totals=USR1` says that tar prints the totals when the signal arrives (before: only "print the total bytes written"). `ar` knows the letters `f`, `P`, `O`, `l` (with the dependencies as the next word) and `V`, as `ar --help` lists them: `ar rcl -lm lib.a x.o` takes `-lm` as the value of `l` and `lib.a` as the archive. Before, `rcl` was the archive and `-lm` the options `-l` `-m`.
- `ip` reads its options only before the object, as iproute2 does: in `ip -s addr`, `-s` shows statistics, and in `ip addr show -s` it is not an option of `ip` (ip takes it as a device name). Before, `ip addr show -s`, `ip a -4` and `ip link show -d` explained the options of `ip`. `kubectl config view -o jsonpath=…`, `kubectl config --kubeconfig f view` and `-n` after `config` are explained (before: unknown options).
- The `bashExplainer.customCommands` setting takes options and operands as lists: an option's `names`, and for each operand whether it repeats (`"repeat": "+"`). A command can also have a `style` and `subcommands`. Before, options were an object (`"-n|--dry-run": "…"`) and `arguments` a list of texts, of which the last repeated; that shape is still read, and a later release drops it. A command in the setting is read only as written there: one named `head` no longer reads `-5` as `-n 5`. Before, the rules of the dictionary applied by the name: `head`, `tail` and `nice` (`-5`), `kill` (`-9` and `-TERM` are signals, `%1` a job), `wait`, `fg`, `bg`, `disown` and `jobs` (job specs), `echo` (only `-n`, `-e` and `-E` are options, and `--` is printed), `let` (no options), `set`, `declare`, `typeset` and `local` (`+x`), `shopt` (option names), `find` (its expression), `jq` (no `--arg=x`), `dpkg`, `dpkg-query` and `dpkg-deb` (`-f=X`), `su` and `flock` (`-c` runs a string), `awk`, `gawk`, `mawk` and `nawk` (`name=value` operands), and `ssh` (the remote command). In the old shape, `takesValue` still counts with any true value, as before.
- In `trap 1 2` and `trap 1 INT`, every word is a signal reset to its default, as bash reads a signal number first. Before, `1` was the command to run.
- `declare`, `local`, `export`, `readonly` and `typeset` read their options up to the first name or `--`, as bash does. `declare -- x=1` says `--` ends the options (before: "Option"). In `declare -x -- -i` and `declare y -i`, `-i` is a name, which bash rejects (before: the integer attribute, and a later `y=1` was explained as arithmetic).
- The summary of a command names its deepest subcommand: `git stash push` and `docker compose -f x run` (before: `git stash` and `docker compose`).
- `locate -r REGEXP` takes the regular expression as its value, as mlocate and plocate do, and `--regex` reads the patterns as extended regular expressions. Before, `-r` was the same as `--regex`, and the regular expression was a pattern.
- `git` knows its other global options: `--git-dir`, `--work-tree`, `--bare`, `--namespace`, `--config-env`, `--exec-path`, `-p`, `-P`, `--literal-pathspecs` and the other pathspec options, `--no-replace-objects`, `--no-optional-locks`, `--attr-source` and `--no-advice`. In `git --git-dir .git log`, `log` is the subcommand. Before, these were unknown options, and `log` a plain argument.
- `ip` reads objects, their commands and its options by a prefix, as iproute2 does: the first one in its table that the word starts. `ip ad s`, `ip ne`, `ip ro g`, `ip m` (maddress), `ip t` (tunnel) and `ip l s` (link set) name their subcommands, and `-stat`, `-bri`, `-det`, `-col`, `-human`, `--stats` and `-fam inet` are options (`-b` is `-batch`). `ip` knows every object and the rest of its options (`-l`, `-0`, `-M`, `-B`, `-iec`, `-t`, `-ts`, `-V`, `-force`, `-b`, `-rc`, `-N`, `-p`). Before, only `a`, `l`, `r` and `n` and the full names were known, and in `ip -fam inet a` the subcommand was lost.
- A function run through a wrapper that clears the environment gets its pitfall: `env -i bash -c f`, `sudo bash -c f` and `sudo -E bash -c f` say that `export -f` does not help there (sudo removes exported functions). `sudo f` suggests passing the definition, `sudo bash -c "$(declare -f f); f"`, instead of `export -f`. Before, `export -f f` hid the pitfall, and `sudo f` suggested `export -f`.
- `sudo -s cmd` and `sudo -i cmd` run the command in a shell, so `sudo -i cd /tmp` runs `cd` there, with no pitfall (before: "command not found"). `watch cmd` runs its words with `sh -c`, as procps does: `watch cd /x` has no pitfall, and `watch f` says that the new shell has no function `f`. `watch -x` still runs a program.
- `env`, `xargs`, `stdbuf`, `flock` and `sudo` accept a long option shortened to a unique prefix, as they do: in `xargs --max-a 2 echo`, `echo` is the command (before: `2`). A prefix the tool finds ambiguous (`timeout --v`, `env --ig`, `flock --no`) is left unknown. They know the rest of their options: `env -v`, `-` and the signal options, `xargs -e`, `-l` and `--process-slot-var`, `flock -o`, `-F`, `--verbose`, `--nonblocking` and `--wait`, and sudo's `-B`, `-C`, `-D`, `-R`, `-N`, `-U`, `-r`, `-t`, `--host` and `--preserve-env=LIST`. In `sudo -h`, `-h` is help (before: it took the next word as a host).
- In `env -S 'ls -l' x`, `x` is an argument of the command that `-S` gives. Before, `x` was the command.
- A builtin run by its path, or by a wrapper that starts a program, is read as the program: `/bin/kill -s TERM 1`, `/bin/echo -e x`, `/usr/bin/test -f x` and `/bin/pwd -L` explain their options, and `env echo` and `sudo kill` show a command, not a builtin. The programs' own options count: in `env printf -v x`, `-v` is the format, and in `sudo kill -n 9 1`, `-n` is unknown (procps kill has no `-n`). Before, a path had no explanation of its words, and a wrapper read them with the builtin's options.
- A jq program with a definition whose parameters have no `)` yet, as in `jq 'def g(x'`, is explained as unfinished. Before, the explanation never ended.
- Shell options, variables, functions and aliases follow the order the script runs in. What a subshell changes (`( shopt -s dotglob )`, `( a=(1 2) )`, `( f() { …; } )`, `$(…)`, a pipeline stage) no longer counts after it. What a function's body changes counts where the function is called, not where it is defined: after `setup() { set -f; }` alone, `echo *.md` is a glob; after `setup`, globbing is off. A body runs with the state of its call: in `main() { setup; for f in *.txt; do …; done; }`, `setup() { shopt -s nullglob; }`, `main`, the loop has no pitfall, and an option set after a definition counts at a later call. `local IFS=,` splits on `,` in its function, and `k() { IFS=-; }; k` changes IFS after the call. Before, any `shopt`, `set -f`, array, `declare -A`, `declare -i` or alias earlier in the text counted, even in a subshell or a function that never ran, and an IFS set in a function did not count.
- An option turned on in a branch or a loop says it may be on: `if …; then shopt -s globstar; fi`, then `ls **/*.ts`, warns that `**` reaches subdirectories only on some paths; extglob, expand_aliases and lastpipe say the same, and so does a variable that is an array on some paths only. Before, a `shopt` in a branch counted as always run.
- An alias is expanded only if `shopt -s expand_aliases` ran before the line was read: `alias ll='ls -l'`, `ll`, then `shopt -s expand_aliases` warns that `ll` is "command not found". `x=1 :` before `set -o posix` sets `x` for `:` only, and `export -f f` after `bash -c f` does not help it. Before, `shopt -s expand_aliases`, `set -o posix` and `export -f` counted anywhere in the script, and so did any `--posix` (as in `awk --posix`); now only `#!/bin/bash --posix` starts in POSIX mode.
- An alias inside `$(…)` or backquotes is expanded when the substitution runs: `alias hi='echo A'; echo "$(hi)"` on one line uses the alias (before: "not in effect yet").
- A Dockerfile RUN warns about a pipe without pipefail unless `set -o pipefail` runs before the pipe in that RUN. Before, the word `pipefail` anywhere in the RUN, in a comment too, silenced it.
- `unset -fv` shows both options (before: `-fv` was a function name).
- A function defined twice is the one defined last before the call (before: the first one). An arithmetic `$p` after `( p='3*4' )` uses the value outside the subshell.

## 0.6.0

- The command a wrapper runs is found correctly, and the pitfalls of wrappers are pointed out. `bash -c 'echo $1' a b` (also `sh`, `dash`, `zsh`, `ksh`, and `-xc`, `-o pipefail -c`) says `a` becomes `$0` and `b` is `$1`; `bash script.sh a b` calls `a` and `b` arguments `$1` and `$2`. `kubectl exec|run|debug … -- ls -la`, `docker run|exec image cmd`, `docker compose run|exec svc cmd`, `podman`, `chroot dir cmd`, `flock file cmd`, `uv run`, `poetry run` and `doas` explain `ls` / `cmd` as the command that runs, with its own arguments. `timeout 5 sleep 10` takes `5` as the time limit and `sleep 10` as the command; `env A=1 cmd`, `sudo A=1 cmd` and `doas A=1 cmd` take `A=1` as an assignment; `nice -10 make` reads `-10` as the adjustment `-n 10`; `su - user` reads `-` as the login option. `sudo cd /root` and `timeout 5 cd /tmp` are both explained as `cd`. New notes: a wrapper (sudo, doas, env, nohup, timeout, nice, xargs, find -exec, chroot, flock, setsid, watch, strace, stdbuf, ionice and others) starts a separate program, so a function of the script or a builtin such as `cd`, `export`, `source` or `read` cannot run (with the fix: `export -f` and `bash -c`, or `sudo sh -c '…'`; also for a function named after `ssh host` or `su -c`); `env FOO=1 echo $FOO` and `FOO=1 echo $FOO` expand `$FOO` before the variable is set; `ssh host ls $HOME/*.log` is expanded by the local shell; `{ echo a; echo b }` has no `;` or newline before `}`, and `{echo a;}` has no space after `{`. Before, `foo` of `bash -c '…' foo` was "the script to run", `ls` of `kubectl exec pod -- ls` was "Pod", the `5` of `timeout 5 cmd` and the `A=1` of `env A=1 cmd` were taken as the command (and `cmd` as its argument), `nice -10` as the options `-1 -0`, `sudo cd` and `timeout 5 cd` were explained differently, and none of these mistakes was pointed out.
- Builtin options are complete and read correctly. Signals of `kill` (`-TERM`, `-SIGTERM`, `-15`) are one option, `kill -l 15` and `trap -p INT` take signals, `kill -n 9`, `wait -p v`, `read -N 3 / -i text`, `exec -a name cmd`, and all value options of `mapfile` / `readarray` take their values, `getopts` names the words to parse, `. file args` the arguments, and `trap INT` resets the signal. `%1`, `%%` and `%name` are job specs. `set -o` / `set +o` alone list the settings. `export -n` removes the export property (it said "name reference"), `export` and `readonly` have their own options, `declare +x` turns an attribute off, `unset -n` is an option, `fc`, `bind` and `suspend` are builtins, `jobs -l`, `disown -h`, `type -p`, `hash -r`, `declare -t` and more are known. `[[ a != pat ]]` says the right side is a pattern, and the example of `[ -n $x ]` no longer calls an empty value false. Before, these were read as combined short options, as PIDs or variable names, or as unknown options.
- Declarations, aliases, special builtins, `>&` and `test` are explained correctly. `LC_ALL=C export X` and `V=1 declare -x Y` stay builtins (they were "external command `export`"); with `-f` or `-F` the names are functions (`export -f fn`); every declaration builtin and `unset` carries "(shell builtin)"; `cmd >& file` says stdout and stderr; the example of `[ $# -eq 1 ]` says "1 argument" (it was `#="1"`); an alias in a bash script without `shopt -s expand_aliases` is "command not found" (it said "replaced by …"); under `#!/bin/sh` or `set -o posix`, an assignment before a special builtin (`V=1 :`) stays after it (it said "only for this command"); the words of `test` are read as an expression like `[ ]` (`test "$a" = "$b" -a -f x`, `test ! -e f`; they were all "Word").
- Shell-language explanations corrected after an audit against bash 5.2. `"$@"`, `"${a[@]}"`, `"${!pre@}"` and `"${@:2}"` are "one word per element" (before: "stays one argument"). The examples of subscripted expansions use an array element (`${#a[1]}` with `a[1]=hello` is 5; before, the scalar `a=hello`, which bash reads as element 0 only). `${1:=x}` and `${@:=x}` say that bash fails with "cannot assign in this way" (before: "assign to `$1`"), and `${@:-none}` is worded with arguments (before: `@=hello`). The home directory is expanded in the word of an unquoted `${x-~/d}`. `${!a[@]:-x}` and `${!v:-x}` are indirection followed by the operator (before: the key list, or the operator was left out). `shopt -s globstar; ls **/*.txt` on one line has globstar on (before: a pitfall note), and so on for `dotglob` and `nocaseglob`. `unset IFS` and a value that is not known (`IFS=$old`) end the earlier IFS note; `set -f` ends "globbed". The end line of a `<<-` here-document is called its end, and the operator `<<-END` (before: body, `<<END`). A `{ }` group in a pipeline, after `&` or in a `coproc` is said to run in a subshell. `[]a]` is a bracket expression, not "no wildcards". `: ${V:=x}` assigns also when `V` is empty.
- New notes: `((i++))` with `i` at 0 has status 1 (`set -e` stops); `exit 256` / `return 300` are taken modulo 256; `local` outside a function fails. A missing `;` or newline before `then` or `do` (`if [ -f a ] then …`, `for x in a b do …`) is reported as a syntax error; before, `then`/`do` looked like an argument and nothing was said.
- Options and operands of external commands are explained correctly in more places: `kubectl logs -f POD` (`-f` is `--follow`, not `--filename`), `git tag -a -m MSG TAG` (`-a` takes no value), `rpm -ivh` (`-i` is install; `-qi` is info), `chmod`/`chown`/`chgrp --reference=RFILE FILE` (every operand is a file), `fdisk -o` (output columns; `-w|--wipe` is the wipe option) and `fdisk -u -l` (`-u` takes a value only with `=`), `systemctl -r`, `date -Iseconds` (the precision is the value of `-I`, not `-s`), `journalctl -b -1` (the boot offset or ID), `seq -f FORMAT 1 10`, and `pip uninstall`/`show` (a package name, not a pin). New: roles of the operands of `uniq`, `zip`, `unzip`, `mktemp` and `pgrep`/`pkill`, and `unzip -l`, `diff -c -N -w -i -B`, `mktemp -p --suffix -u -q`, `xargs -i`. Before, these were shown with the wrong meaning, the next word was taken as a value, or the words were left as "Word".
- An option with its value glued on and partly quoted is read as the option and its value: `awk -F'|'`, `cut -d','`, `sed -e's/a/b/'`, `grep -e'x'`, `tar -C'/tmp'`, `awk -F' '` and `awk -F"\t"` (the value reads "`,` after quote removal", and a `-e`/`-F` value in another language is broken down). Before, the whole word was a stray argument, so the next word (the awk program, or a file) took its place and the example was wrong or empty.
- jq options are complete and read right: `--arg`, `--argjson`, `--slurpfile` and `--rawfile` take a name and a value (also in kislyuk/yq), `--indent N`, `-f FILE` (then the first operand is an input file), `--args` and `--jsonargs` (the operands are strings or JSON values, not files), `--tab`, `-S`, `-a`, `-j`, `--raw-output0`, `--seq`, `--stream`, `-C`, `-M` and `-L`. The example follows `-s` (the file holds the values, one per line, and the filter reads them as one array: `jq -s length` gives their number) and `-j` (no newlines). Before, `jq --arg n foo '.name = $n' in.json` took `foo` as the filter, and `-s` and `-j` were ignored.
- jq: destructuring (`. as [$a, $b]`, `{k: $v}`, `{$a}`, `{(expr): $v}`, `?//`, in `as`, `reduce` and `foreach`) and `label $x | … break $x` are explained and run in the examples; the sample input fits `.[] | @csv`/`@tsv`, `contains(…)`, `inside(…)`, `index(",")` and `. + [..]`/`. - [..]`/`. + {…}`; `test(re; "x")` ignores whitespace and comments in the pattern; `index`/`indices` on an object give null (and fail on a number or a boolean); `fromjson` gives jq's message for a non-string. Before, these filters were "Could not parse", the sample input made `.[] | @csv` and `contains("a")` fail, and `test("v a"; "x")` was wrong.
- In `[[ $x =~ \bfoo ]]` the unquoted backslash before an ordinary character is removed by bash, so `\b`, `\w`, `\s`, `\d` and `\<` are the plain characters `b`, `w`, `s`, `d` and `<`; the regex is explained so, with a warning that says to keep the regex in a variable (`re='\bfoo'; [[ $x =~ $re ]]`) or to use `[[:space:]]`. Before, they were explained as the GNU word boundary and classes, which bash never passes to the regex.
- The sed examples and explanations follow GNU sed more closely. An empty match right after a match is skipped, as GNU sed does: `s/x*/-/g` on `x xx` gives `- -` (before, `-- --`), `s/b*/X/2` on `b bb` gives `b X`; `0,/re/` can end on line 1 (before, `0` read as "line 0" and the example ignored it); `sed -z` shows no example (before, it was run on lines); `s/o/0/2g` says "every match from the 2nd on" (before, "every match"); an empty pattern (`s//x/`) says "the last regex"; an incomplete `\{` in `grep 'a\{1'` is an error (before, a literal brace).
- awk is explained and run more correctly. A comma inside a call in a pattern, as in `match($0, /re/) { … }`, no longer makes a "range pattern"; `name=value` operands (`awk '{print $1,$2}' OFS=, f`) are described as assignments and used by the example (before, "target file"), and escapes in `-v` and `-F` values are processed (`-v OFS='\t'` is a tab, `-F '\\|'` splits at a bar); `$0 = …` says that the fields are split again, `delete a` that the whole array is emptied, and `RS = ""` that it is paragraph mode. An example that needs another `RS`, a `CONVFMT`, the 4th argument of `split` or more `printf` formats than values is not shown, as it could not match awk.

- `find` is explained as it behaves. `-mtime +7` is "at least 8 days ago" (days are whole, the fraction is dropped; `-mtime 7` is from 7 to 8 days, `0` the last 24 hours); `-size` is rounded up to the unit, so `-size -1M` is only empty files and a bare `-size 10` counts 512-byte blocks; `-perm 644`, `-644` and `/222` are told apart; `-newermt`, `-newerXY`, `-anewer`, `-cnewer`, `-samefile` and `-links` are known (before, "Option (not in the dictionary)" and their values read as options); `-maxdepth` after a test gets a note that it is global. Before, these read "modified more than 7 days ago", "smaller than 1M" and "permissions 644".

- A glob pattern is explained the same way wherever it appears: the right side of `=`, `==` and `!=` in `[[ ]]`, `case` patterns, arguments (`ls *.txt`, `rm -f log-202[0-4]-??.txt`), the patterns of `${x#pat}`, `${x##pat}`, `${x%pat}`, `${x%%pat}`, `${x/pat/rep}` (and `//`, `/#`, `/%`), extglobs, and the quoted pattern of `find -name`. ## 0.5.0

- The parser is now [unbash](https://github.com/webpro-nl/unbash), a small JavaScript parser, in the extension, the web page, the command-line tool and the Language Server. Before, it was tree-sitter-bash running as WebAssembly. The `.vsix` is a quarter smaller (703 KB, was 947 KB) and the web page downloads 1.5 MB less (no `.wasm` files); a large script is parsed about three times faster; nothing is loaded at start-up. Scripts that the old grammar misread are read as bash reads them: `cat <<EOF; cmd` (the delimiter is `EOF`, not `EOF;`), a pipeline followed by a later `&&` line (tree-sitter-bash#347), `for i do`, `<<-` with tabs, `coproc`, `[ ]` with escaped parentheses (`[ \( a = b \) -o c = d ]` is grouped), `[ ! = a ]`, and a here string after `}`. An unfinished script (`{ echo`, `case $x in`, `echo "abc`) is explained with the parts it has, not as a syntax error.
- About 400 more commands are explained, with their frequent options, instead of "not in the dictionary": the ones named in the LPIC-1/2 and LinuC-1/2 objectives (`fdisk`, `parted`, `mdadm`, `pvcreate`/`lvextend`, `grub-install`, `rpm`, `zypper`, `chage`, `at`, `hwclock`, `nmcli`, `tcpdump`, `nmap`, `rndc`, `smbclient`, `iptables` options, `firewall-cmd`, `semanage`, `iostat`, `sar`, `virsh`, `ansible-playbook`…), basic ones (`man`, `locate`, `whatis`, `cal`, `w`, `last`, `shutdown`, `reboot`, `init`, `traceroute`, `tree`, `chroot`, `tmux`, `/usr/bin/time`…) and the common macOS tools (`open`, `pbcopy`, `say`, `caffeinate`, `diskutil`, `launchctl`, `networksetup`, `mdfind`, `xattr`, `codesign`, `plutil`, `sips`, `system_profiler`, `dscl`, `lipo`…). The summary line is unchanged. Before, the redirections were children of the command, and its description covered them.
- A script with Windows line endings (CRLF) is explained as if it had LF, and a warning (`crlf`, on the last word of the first such line) says that bash reads the CR as part of the last word of each line (`fi` becomes `fi\r`), so the script fails. Before, the extension said nothing, and the unbash path read `fi` as a command.

A later `alias` of the same name replaces the earlier one. Before, an alias applied to the whole file, and the first definition always won.

- An array element with spaces in its subscript, `a=([1 + 1]=x)` or `declare -A m=([a b]=1)`, is explained as one element with an index (2) or a key (`a b`), as bash reads it up to the `]`. Before, the tree-sitter path split it into three words (`[1`, `+`, `1]=x`) and said three elements. `[1 + 1] =x`, `[1 + 1] = x` and `x[1 + 1]=x` are still separate words, as in bash.

- `[ 1+1 -eq 2 ]`, `[ x -eq 2 ]` and `[ 1.5 -eq 1 ]` say that `[ ]` reads only integers for `-eq` and the like, so the operand is an error (integer expression expected), and `[[ ]]` would calculate it. `[[ 1+1 -eq 2 ]]` says that it is read as arithmetic (2). Before, they said "numbers are equal" only.
- An array element whose key is quoted, such as `["a b"]=1`, `[']']=3` or `['q r']=z` in `h=( … )`, is explained as an element with a key and a value, like `[c]=2`; the key is shown without its quotes (`a b`). Before, it was a "concatenation" of `[`, the string and `]=1`. The closing `]` is the first one outside quotes, expansions and nested `[ ]`, as in bash, so `['a=b']=c` and `[a\]]=c` work too.
- `${!prefix@}` and `${!prefix*}` are explained as the list of the names of the variables that start with the prefix (`@`: separate words, `*`: one word inside double quotes), with the `@` and `*` described as such. Before, they were an "indirection" through a variable named like the prefix, the `@` was called a transform, and `${!zq_*}` made the explanation fail. `${!x@Q}` says indirection first, then the transform.
- `=` and `==` in `[ ]` and `test` are explained as comparing plain strings (`[ a = a* ]` is false). The note that the right side is a glob pattern is shown in `[[ ]]` only; before, `[ ]` had it too.
- Extended globs (`+(a)`, `@(a|x)`, `*(b)`, `?(a)`, `!(a)`) in `${s#…}`, `${s//…/…}` and the like are explained as extended globs that need `shopt -s extglob`. Before, they said "contains expansions, so it is decided at run time"; that is said now only when the pattern has a `$…` or a backquote.
- An unclosed backquote, `$(` or `$((` in the pattern of `${s^^…}`, `${s#…}`, `${s:-…}` and the like, followed by a backslash at the end of the text, no longer makes the unbash path throw. Before, unbash ended such a part past the text, and the explanation failed.
- A backquote substitution inside double quotes is read as bash reads it: the backslash before `$`, a backquote, `\` and `"` is removed before the command is parsed, so `` echo "`echo \"x\" y`" `` shows the string `x` (the unbash path mapped the positions, but the text still had the stray backslash). `\\\\` in a backquote is now `\` (one backslash), not `\\`, in both parsers. Before, the explanation of such words removed only the quotes.
- `[[ x =~ "$re" ]]`, `=~ 'a.c'` and `=~ a"."c` say that the quoted part is literal text, not a regex (a variable that holds a regex is written `$re`, not `"$re"`). Before, they were explained as a regex, as the unquoted form is.
- `${p//\//_}`, `${p/#\/a/X}` and the like: the header splits the pattern and the replacement at the first slash that is not escaped, quoted or inside an expansion. Before, it split at the `/` of `\/` (`p` 内で `\` に一致する部分を `/_` に置換).
- `${s:1?2:3}`, `${s:(1?2:3)}` and `${s: a?1:2 :1}`: the `:` that closes a `?` belongs to the ternary of the offset, not to the length, as in bash. Before, the offset was `1?2` and the length `3`.
- `n>&m-` and `n<&m-` are explained as moving descriptor m to n (copy, then close m), and the note on the order of redirections tracks it. Before, `4>&3-` was "write both stdout and stderr to the file `3-`".
- `{name}>file`, `{name}<file`, `{name}>&1` and `{name}>&-` are explained: bash picks a free descriptor from 10 up and stores its number in the variable, or, with `-`, closes the descriptor the variable holds. Before, `{fd}` was read as a descriptor named `{fd}` (unbash path).
- `for i in; do …; done` and `select i in; …` say that the empty list means the body never runs; only a loop with no `in` goes over `"$@"`. `select` is explained as a menu, not as a `for` loop.
- `${s~~}` and `${s~}` are explained as swapping the case (every character, or the first), with an optional pattern. Before, they were read as the plain variable `s`.
- The examples of `${s,,[HL]}`, `${s^^pat}`, `${s^pat}` and `${s,pat}` are computed with the pattern, which limits the characters that change (and, for `^` and `,`, tests the first character only). Before, they showed the result without the pattern (`hello world`, where bash gives `hEllO World`).
- Bracket expressions in patterns are read as bash does: `[[:alpha:]]` is one letter (the example listed `a]`), and `[]]`, `[!]a]`, `[\^a]`, `[a\]b]`, `[[.a.]]` and ranges are handled in `case` examples, file globs and the descriptions of patterns. Before, the first `]` always closed the expression.
- `a[1]+=x` is explained as appending to the element (`b` becomes `bx`), also for associative arrays (`m[k]+=x`); with `declare -i` it adds (`c[0]+=5`). Before, it read "Assign to element".
- Tilde expansion is explained in ordinary arguments: `echo ~`, `ls ~/x`, `cd ~`, `~user/x`, `~+` and `~-` get a child saying what they become. Quoted `"~"`, `x~` and `--o=~` get none, as bash does not expand them. Before, only the tilde in an assignment (`x=~/y`) had a note, and `~user` and `~+` were described as the home directory.
- A function is called only after its definition has run, as in bash: `echo -- -n; echo(){ …; }` explains the first `echo` as the builtin (with a note that the function comes later), and `command echo` and `builtin echo` explain the builtin's arguments, not "argument $1 to the function". A call inside a function body still sees functions defined further down. Before, a function was applied to the whole file.
- `>&${fd}` and `<&$x` are explained as duplications of the descriptor the word expands to (a number), with `>&word` as a file only for other text. Before, `>&${COPROC[1]}` was "write both to the file". `coproc` is explained (it was the raw `coproc_statement`), and `COPROC` and `COPROC_PID` are described; the wrong example `COPROC=(a b c)` is gone.
- Brace expansion is explained for plain words in the unbash path too (`a{b,c{d,e}f}g`, `x{a,b}`), and `{echo,hi}` as a command name runs `echo hi`. `{1..$n}` is said to be no range (braces go before variables), and `eval` is said to expand it later.
- `-eq`, `-lt` and the like say how their operands are read: decimal in `[ ]` (`010` is 10, `0x10` is an error), arithmetic in `[[ ]]` (`010` is octal 8, `08` is an error). Before, both said "numbers are equal".
- `set -f` / `set -o noglob` turn off the glob explanations and examples after them, until `set +f` / `set +o noglob`. `set +f` is "undo `-f`: enable globbing again"; before, it read "disable globbing".
- `&` in the replacement of `${s/b/[&]}` is explained as the matched text (bash 5.2, `patsub_replacement`), and a quoted `&` (`\&`, `"&"`) as the character.
- Notes: unquoted expansions say which `IFS` they split on, and an assignment to `IFS` says what it does; `$y` on an array is its first element; `$_` after an assignment-only command is empty; `$x` inside `$(( ))` is pasted as text, unlike the name `x`; a redirection after a function body is applied on every call; the `$variables` of a `trap` string are expanded when it runs (single quotes) or now (double quotes).
- `time ls -a` explains `ls` itself ("List directory contents") under `time`, as it does after `time` in a pipeline; before, only its options were shown, and the command was left out.
- `time` is explained as timing the whole pipeline after it, as bash does: `time cat f | sort` is one timed pipeline, with an example for the whole pipeline; it was `time cat f` piped into `sort`. The commands after `time` are checked like any other, for dialects (`time echo -e x` under dash) and pitfalls (`time read x`, `time rm $f`); they were left out.
- A redirection after the last command of a pipeline or list belongs to that command, as in bash: in `echo A && echo B > f` only `echo B` is redirected, and `echo a | cat 2>/dev/null` redirects `cat`; both were explained as redirecting the whole pipeline or list.
- `! a | b` is explained as negating the exit status of the whole pipeline, as bash does (`! true | false` succeeds); it was explained as negating only `a`.
- What follows a here-document's delimiter on its line is explained as bash reads it: in `cat <<EOF | tr a-z A-Z && echo after`, `tr` and `echo` are commands of the pipeline and the list, with examples and pitfalls; they were taken as a part of the here-document and not explained. Redirections there (`cat <<EOF > out.txt`) are listed beside the here-document, not under it.
- `a | time b` is explained as running the program `time`, as bash does: `time` is a keyword only at the start of a pipeline (`a && time b` times `b`); it was explained as timing `b`.
- Under zsh, a syntax error nested in a larger one is also reported as "could not be parsed" on its line, as every other error is.
- An unfinished script (`if x; then` with no `fi`) no longer lists a keyword of no width ("End of the `if` statement") for what is missing.
- A bare `seq` (and `seq` with more than three numbers) gets no example, as GNU seq reports an error for it; before, explaining the line threw and no explanation was shown. `printf` with a backslash at the end of the format (`printf 'a\\'`) or before a newline is explained and prints the backslash, as bash does, instead of throwing. `printf` formats that bash rejects (`\x`, `\u` without digits) or that write bytes which are not text (`\400`, `\xe9`, `\ud800`) get no example; before, they showed a wrong output (`\x` lost its `x`, `\400` printed `Ā`).
- `${#}` is explained as the number of arguments, like `$#`, and `${##}` as the length of `$#`; before, they were "remove the shortest prefix matching ``" and "remove the prefix `#` from `##`". `${#@}` and `${#*}` are the number of arguments (not a length in characters). `${##x}`, `${#-x}`, `${#:-x}` and `${#%3}` are `$#` with an operator, as bash reads them; before, they were a syntax error or had a wrong example (`#=hello`). `$?`, `$$`, `$!` and `$-` with an operator are shown with their `$`.
- Numbers in arithmetic are explained with their base and decimal value: `2#1010` is binary 10, `0x1F` is hexadecimal 31, `010` is octal 8, `64#@` is 62. Numbers bash rejects (`08`, `2#2`, `1#0`, `0b11`) are flagged. Before, `0x1F` was "variable `0x1F`" and the others were just "number". The same rules read the offset and length of `${s:0x1:010}`.
- The comma operator in `$((x=3,y=x++*2,x+y))` and `(( a=1, b=2 ))` is explained: the expressions run left to right and the last one gives the value.
- A word with quotes or backslashes shows the string it becomes: `h\i` is `hi`, `\$HOME` and `$'\x24HOME'` are the text `$HOME` (nothing is expanded). A command name made of such parts is explained as the command it spells when that is known: `$(:)e\c'h'"o"` is `echo`, `'echo'` and `e\cho` too. Before, it was "Run the expanded value as a command", or an unknown command named `'echo'`.
- `${*: -1}` and `${@: -2}` count from the last argument ("the last argument; it is not `$-1`"); before, they said "from `$-1`". For arrays, a negative offset counts from one past the highest index, which on a sparse array is not the last element; the length is "1 element" and "1 character" in the singular. The offset and length can be written `0x1` or `010`, as bash reads them.
- `${!#}` is explained as the last argument (with a checked example, `r` for `p q r`); before, "When `#=HOME`" with the value of `$HOME`.
- The replacement in `${s/#h/\}}` is shown after quote removal (`}`, with the example `}ello world`); before, it showed `\}` and `\}ello world`. A replacement with `&` (the match, in bash 5.2) gets no example.
- In a `case` with `;&` or `;;&`, the statement says what the three endings do, and the branch after one says it is run without its pattern (`;&`) or tested again (`;;&`); a `*)` after them is no longer "runs when nothing else matched".
- `local -n r=$1` is explained as making `r` another name for the variable named by `$1`, and a later `r=7` says it sets that variable; before, both were plain assignments to `r`.
- `PIPESTATUS` and `BASH_REMATCH` are described as what they are, with examples that run (`false | true` gives `1 0`; `[1]` is the text of group 1, `${#BASH_REMATCH[@]}` is the number of groups + 1); before, the examples were `PIPESTATUS=(a b c)`.
- `$[1+2]` is marked as the obsolete form of `$((…))`.
- Constant array indexes are evaluated: `${a[1+1]}` is "an arithmetic expression: 2", `${a[010]}` is 8, and `${a[-1]}` is "the last element".
- `z=2 echo $z` says `$z` is expanded before the assignment applies (it is empty if unset), and `x=1 y=$x` says `$x` is already set because assignments run left to right.
- Brace expansions that the parser splits into words (`{a,b\,c}`, `{,}`, `{a..e..2}`, `project/{src,test}`) are one "Brace expansion" with the words they give: `{a,b\,c}` is `a` `b,c`, and `{,}` is nothing. Before, they were a "Concatenation" of the pieces `{`, `a,b\,c` and `}`.
- A `case` pattern made of several pieces is one pattern: in `[\)]|"("*)` the second pattern is `"("*` (a literal `(` and anything after it), and the `|` tells the patterns apart; before, it was split into `"("` and `*`, as if the line had three patterns.
- The default word in `${u-'x'}` is shown after quote removal: unquoted it gives `x` (and `${u-'}'}` gives `}`), and only in double quotes (`"${u-'x'}"`) do the single quotes stay; before, both examples showed `'x'`. The same holds for `+`, `=`, `:?` and in a here-document.
- A variable declared with `declare -i` (or `local -i`) is explained as taking arithmetic: `n=3+4` is evaluated (7), and `n+=1` adds (8) instead of appending text (`71`); before, it was "append to variable".
- Words after the format of `printf` are values, as in bash: `printf '%d|' 1 -0` prints `1|0|`; before, `-0` was called an option. Builtins read options only up to the first operand (`echo a -n` prints `a -n`, `declare x -i` is an error for the name `-i`), and `echo` knows only `-n`, `-e` and `-E` (`echo -x`, `echo -nx` and `echo -- a` print their words).
- A quoted right side of `==`, `=` and `!=` in `[[ ]]` is explained as literal text (`[[ x == "*" ]]` is false); before, it was "a glob pattern". For `*"$y"*z` the quoted part is literal and the rest is a pattern.
- In `declare -A m=([1+1]=v)` and `m[1+1]=v` the key is the string `1+1`; in an indexed array `i=([1+1]=v)` the index is evaluated (2), as `${!m[@]}` and `${!i[@]}` show in bash (`1+1 2`). `${m[k]}` says "key" for an associative array. Examples for an associative array no longer list `0 1 2` for `${!m[@]}` (the keys come in no fixed order); `${#m[@]}` is 3 for `([a]=1 [b]=2 [c]=3)`.
- `"$@"x` and `p"${a[@]}"q` are explained as one word per element, with the text before glued to the first one and the text after to the last (`[a]`, `[b cx]`); before, "the parts are joined into one word".
- `{Z..a}` is listed with its eight words (the lone backslash is gone after quote removal and stays as an empty word, shown as `''`), also on the unbash adapter, and `{01..10..3}` says that a leading 0 pads every number.
- The arguments of `let` are explained as arithmetic expressions, one each, left to right: `let "y = x << 1" z=y%3` shows the assignments, the shift and the modulo; before, they were a string and a plain word. The value of a constant one is shown (`let 0x10+1` is 17).
- `IFS=, read -ra p <<< "a,b,,c,"` shows the line it reads (`"a,b,,c,"`) and what is stored (`a`, `b`, an empty field, `c`), and a note says that a separator that is not whitespace keeps empty fields and a trailing one adds none; before, the example used a made-up line.
- An arithmetic expansion of constants that overflows says the result wraps around (`$((1<<63))` is `-9223372036854775808`: bash integers are 64-bit); the shift operators of constants are computed.

- About 70 more commands that distributions install by default: `flock`, `journalctl`, `ping`, `dig`, `lsof`, `free`, `top`, `crontab`, `setfacl`, `unshare`, `nsenter`, `mkfs.ext4`, `ssh-add`, `shuf`, `vim`, … (with their frequent options).
- `[[ -f a && $x =~ re ]]`, `[[ -f a && $x = y ]]` and `[[ $x = *.txt || $x = *.sh ]]` (`=` and `=~` next to `&&` and `||`, `=` with a glob on the right), `[[ $x = *"$y"*z ]]` and `[[ $x = ~/a* ]]` (a pattern of several parts, or starting with `~`, after `=`, `==` and `!=`), `[[ ! $x =~ re ]]`, `[[ ! $x = y ]]`, `[[ ! $a -eq 1 ]]`, `[[ ! $a < b ]]` and `[ ! a = b ]` (`!` negates the whole test), and `${s:$i}`, `${s:$i+1}` and `${s:$i-1:1}` are read as bash does; the parser's grammar is patched so that `=` and `=~` in `[[ ]]` bind tighter than `&&` and `||`, `=` takes a pattern like `==` does (with any number of quoted and expanded parts in it), `!` binds looser than the comparison after it, and a variable can be the offset or length of a substring, with or without arithmetic after it. Before, `[[ -f a && $x =~ re ]]` was read as `(-f a && $x) =~ re`, `[[ $x = *.txt || $x = *.sh ]]` as a syntax error, `[[ ! $x =~ re ]]` as `(! $x) =~ re`, and `${s:$i}` was a syntax error.
- Aliases and functions that distributions define for interactive shells are explained, with what they stand for on each system, as checked in the files the distributions ship: Ubuntu's `ll`, `la`, `l` and `alert`; Fedora / RHEL's `ll` and `l.`; openSUSE's `ll`, `la`, `l`, `ls-l`, `o`, `..`, `...`, `cd..`, `+`, `-`, `md`, `rd`, `rehash`, `beep`, `unmount`, `remount` and `xd`; Git for Windows' `ll`. A note says they depend on the system and are missing in scripts, and what to write instead; in Markdown code blocks, typed into a terminal, the note is milder.

## 0.1.0

First release.

### Explanations

- Line-by-line explanations of shell scripts in English and Japanese: commands and options (about 120 commands and builtins, with combined flags, option values and subcommands), operators, redirections and their order, `${…}` expansions part by part, control flow, and well-known idioms.
- The languages inside arguments: regular expressions (BRE, ERE, PCRE), sed scripts, awk programs, jq and yq filters, perl one-liners, `printf` and `date` formats, `find` expressions, `chmod` modes, `sort -k` / `cut -f` / `tr` sets, `getopts` / `getopt` option strings, and `git log --pretty` / `--date` formats.
- Worked examples with sample input and output, for regexes, sed, awk, jq, yq, perl, text filters, whole pipelines, expansions, `printf`, globs, tests, `xargs`, `read`, `getopt` and `git log`. They are computed by built-in code that the tests check against the real tools.
- Your own commands, described in `bashExplainer.customCommands`.

### Ways to show them

- A hover for the line under the mouse, or for the cursor line with `Ctrl+K Ctrl+E` (`Cmd+K Cmd+E` on macOS).
- A panel that follows the cursor, inspired by regex101: edit an example's input and watch the output change, with matches and capture groups highlighted; fold the tree, copy it as Markdown, switch the shell or yq for the file, and search a quick reference.
- An inline one-line summary at the end of the cursor line.

### Other shells and other files

- Constructs that POSIX sh, dash, ash, yash, ksh, mksh or zsh do not support are pointed out, and behaviour that differs from bash is noted. The shell is detected from the shebang, a `# shellcheck shell=` line or the file name.
- Shell code inside Dockerfiles, Makefiles, GitHub Actions and GitLab CI YAML, `package.json` scripts, Markdown code blocks and Python `subprocess` / `os.system` calls is explained too, with warnings about script injection, Docker `RUN` pipes without `pipefail` and Python commands passed without `shell=True`.
- yq commands are recognised as mikefarah/yq v4, kislyuk/yq or mikefarah/yq v3, with the first v4 release that has what the command uses.

### Problems panel

- Warnings in the Problems panel, with quick fixes where the rewrite keeps the meaning (`[[ ]]` → `[ ]`, `==` → `=`, `source` → `.`, `&>` → `> … 2>&1`, and more).
- `# bash-explainer disable=<code>` and `disable-file=<code>` comments, and `bashExplainer.diagnostics.ignore`, to silence them.

### Privacy

- Works offline by design: no network access, no AI, no telemetry, no external processes. A CI check keeps it that way.
