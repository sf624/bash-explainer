# Notes for Claude Code

README.md ("Contributing") has the commands and the rules for tests, coverage and releases; read it first. This file adds what it does not say about this repository.

## Working tree

- `test/fixtures/sample.sh` is a curated tour of every feature, in sections headed `# --- Title ---`; it is also the web page's shell sample. Keep every line explained correctly (`npx tsx test/dump.ts test/fixtures/sample.sh en`) and every example kind covered. Check the dump after edits.
- `test/fixtures/playground.sh` (gitignored, created from `sample.sh` by the F5 pre-launch task when missing) and `test/fixtures/hosts/*` are the maintainer's playground for trying explanations in VS Code; edits there are theirs.
- Japanese strings in `src/`, and README.ja.md, follow [docs/japanese-style.md](docs/japanese-style.md); a test checks them.

## Changelog

- CHANGELOG.md is read by users (GitHub Release notes, the Marketplace); README "Contributing" has its format and the release steps. Write one bullet per user-visible change under `### New`, `### Changed` or `### Fixed` of `## Unreleased`: one or two short sentences with the point a user sees, never a paragraph. Write "Before, …" only when the behaviour changes in a way users will notice, not for every fix.
- Fine-grained examples and the earlier behaviour go into `docs/changes/unreleased.md` (at release, renamed to `docs/changes/<version>.md`), linked from the version's section. When a change is a fix of a kind already listed (one more construct explained as bash does, one more tool option), extend that bullet's entry in the details file with a few words or an example; do not grow the bullet or add one.
- No tests, CI, refactors or design (the semantic model, specs) unless users see the effect, and then describe the effect. Keep compatibility notes (deprecated or changed settings, removed features, minimum VS Code version) explicit, in the bullet.

## Tests and coverage

- Every line and branch of `src/` must be taken by the unit tests (`coverage-floors.json` is empty). Measure as CI does: Node.js 24 and `npm run coverage` (it sets `TZ=UTC`), then `npm run coverage:check`.
- Prefer tests that compare with the real tool: GNU sed, gawk, perl, jq, bash, git, GNU coreutils, PyYAML for kislyuk/yq. Most `test/examples-*.test.ts` already hold such tables; add cases there. These tests have found many bugs, so when the tool disagrees, fix the code (with a CHANGELOG line under "Unreleased") rather than the expectation.
- Behaviour that differs between tool releases (jq 1.7 vs 1.7.1, mawk vs gawk) is left out of the comparisons and tested on its own.
- A branch no input can reach is removed (or becomes a non-null assertion when the grammar guarantees the node); a guard against a bug elsewhere gets `/* c8 ignore … */` with a comment. Put `/* c8 ignore start */` before `} catch`, so the catch's own branch is left out too.

## Explanations

- An explanation that contradicts bash or the tool (a label, a role, a note, an example) is a bug: fix it now, with a test against the real tool. A missing explanation is acceptable for a rare edge case, but representative usage (tutorials, LPIC/LinuC material) should be explained.
- The explainer also teaches bash itself. Keep visible where bash's own reading ends (its commands, words, assignments and redirections, as bash-ast shows them) and where a command's or our further reading begins (options and arguments from a spec, subcommands, embedded languages, commands inside `$( )`). Features and designs should help a reader learn the language, not only the commands.
- An example section is input only for what the command really reads: its stdin, a file it reads, or arguments it takes as data; anything else says what it is (the moments `date` runs at, `$ARGS`). Its label names where the data is read from (`入力: \`a.json\`（中身の例）`, `入力: 標準入力（\`b.json\`、中身の例）`, a pipe, a here-string's real text), from `streamLabel` in src/examples/source.ts. Files read as one stream get one section each and one output; a tool that prints each file apart (head, tail, wc) shows that; a glob or a variable is one section labelled with the word. A file operand makes a tool ignore stdin (`jq . a.json < b.json` reads only a.json), and nothing read means no input section, only a note (`jq -n`, awk `BEGIN` alone); with `jq -n`, what `input` or `inputs` reads is labelled so ("Input read by `inputs`: `a.json` …"). A file named twice is one section, read twice. What a command reads, and how it works on several files, come from its spec (`io` on operands and values; `eachFile` of the command or of an option given: `head` prints headers, `sed -s` reads each apart, `sed -i` rewrites each) and the syntax around it (`inputSource`, `stdinOf`; a pipe brings the output of the stages before when it is known), not from its name.
- Conventions and the language both count. Where the syntax does not change whether a line is correct, follow the convention and add a short note on the syntax (a subcommand is shown as a command, with "to the shell it is an argument"). Where it does, show the syntax (`[` is a command and `]` its last argument; a wrapper runs its command as a separate program).
- The reference for the language is the GNU Bash Reference Manual (bash 5.2). Check coverage section by section, not with a few examples. Read it from the bash-doc package (`/usr/share/doc/bash/bashref.html`, or `info bash`), not from www.gnu.org: fetching many pages from there got this machine blocked.
- A token cites the sections of the manual it is about (`Token.refs`, from src/refs.ts or the name resolution), and a note that states a fact of the models comes from the message catalog src/messages.ts (id, ja/en text, sections; `cx.say(fact(…), n)` or `cx.note(fact(…), n)` in src/explain/). Add a new such note to the catalog, not inline; a section must be in src/manual.ts (bash 5.2 numbers, gnu.org pages), or another reference in src/references.ts (a Linux manual page: `execve(2)`), which every output and the web hover's link allow-list read. Style checks stay in src/pitfalls.ts.

## Design

- [docs/roadmap.md](docs/roadmap.md) holds the agreed order of the work, and what waits on the maintainer. Read it before starting or proposing work; update it in the same PR that starts, finishes or drops an item, and add an item whenever the maintainer agrees to a plan that is not done at once.
- [docs/design/README.md](docs/design/README.md) is the index of the design documents, with the status of each. When a document's status changes (a step done, a plan finished), update its row there in the same PR.
- [docs/design/semantics.md](docs/design/semantics.md) is the plan: A, command specs read by one argument interpreter (`src/argv/`); B, a semantic model after the manual (`src/semantics/`); C, the bash-ast test. Do not add one-off fields to `src/dict/types.ts` or name checks to `src/explain/`; extend the spec or the model instead, or say why not.


- The refactoring plan (one source per fact, in three stages) is [docs/design/refactor.md](docs/design/refactor.md). Every refactoring PR lists the finding IDs it addresses and updates the traceability table there in the same PR.
- The plan that thinned src/analyzer.ts (modules in src/explain/, one context per line, layers without cycles) is [docs/design/analyzer.md](docs/design/analyzer.md), done; its steps kept every explanation byte-identical (test/snapshot.ts).
- The explanation is in src/explain/, one module per part of bash (words, tests, redirections, arguments, commands, compound commands…), as functions `(cx: Explainer, n, …)`. The line's context (src/explain/context.ts) is their only state, and its methods (`note`, `say`, `example`, `enclosing`, …) the only way to add to the line. A module imports only those below it (analyzer.md, 2.5); test/explain-imports.test.ts fails on a cycle and on a command name compared there. src/explain/dispatch.ts calls the module of each node type, and src/analyzer.ts only builds the context, walks the line and gathers its notes and examples: add a new explanation to the module of its part, not to these two.
- bash 5.2 is the default reference; `bashExplainer.bashVersion` explains a script as bash 5.3 runs it ([docs/design/bash-versions.md](docs/design/bash-versions.md): the inventory of 5.2→5.3 differences and the steps). A construct one version lacks is explained as it is, with a dialect-style issue for the other (`SINCE` in src/bashversion.ts). Tests run a real bash 5.3 from `$BASH_EXPLAINER_BASH53` (GPL: a separate program, never published).
- The extension prefers the local (UI) extension host in a remote window (`"extensionKind": ["ui", "workspace"]`), so that it can read every colour theme ([docs/design/theme-colours.md](docs/design/theme-colours.md), "Where the extension runs"). It must keep needing nothing from the remote machine: no process, no file of the workspace, no environment.
- The maintainer's F5 runs through Remote - WSL (VS Code on Windows), so the extension under development runs in the WSL extension host and sees only the extensions on that side (no colour themes): a development extension runs where its folder is, whatever its `extensionKind`. To simulate a remote window locally, install the .vsix and set `extensions.experimental.affinity` (VS Code ignores it for development extensions); for a real one, run the VS Code server of the same commit on 127.0.0.1 with folders of its own and connect a window to it with a test resolver (proposed API `resolvers`, `--enable-proposed-api`), as docs/design/theme-colours.md ("Tests") describes.
- bats test files are a host kind ([docs/design/bats.md](docs/design/bats.md)): the extractor rewrites `@test "x" {` into the function bats makes of it, and bats' own functions (`run`, `load`…) are specs in `src/dict/bats.ts` that apply only in that kind (`ShellRegion.commands`). `test/bats-real.test.ts` checks what we say with bats-core (the devDependency `bats`, MIT, run as a program).
- Every product parses with the unbash adapter (`src/syntax/adapters/unbash.ts`), and only that file may import unbash (test/syntax-boundary.test.ts); everything else reads the model of `src/syntax/tree.ts`. Tests that explain scripts build the parser with `createUnbashParser()`. tree-sitter was removed (docs/design/syntax-tree.md, step 6).
- No bundle may load or contain wasm; test/offline.test.ts checks it.
- unbash reads `time cmd` as a `time_statement`, `select` as a `select_statement`, `coproc` as a `coproc_statement`, and `(( ))` alone as an `arithmetic_command`. It accepts what bash rejects only at run time (`${x@Z}`, `${#a-b}`, `${(f)var}`: bad substitution), so the analyzer says so itself (`${(f)var}` only when the shell is not zsh; with zsh, the dialect check marks the line as not parsed). It also accepts a bare `echo (`, which bash rejects (a limit, listed in README Limitations). It ends `${ echo a }` at the `}`, which bash 5.3 reads as an argument of `echo`; `braceTakenAsWord` (src/syntax/tree.ts) finds such a `}`, and the token and the issue `funsubBrace` say so.
- A script with CRLF line ends is read with each CR before a LF masked as a space (same length); `SyntaxTree.carriageReturns` lists them and `documentIssues` warns once (`crlf`).
- A statement over several lines that is not a block is explained whole, with no current line (see `sub` in `src/explain/context.ts`).
- The tree keeps a body's statements and their `;` and `&` as its children (the model's `list` is an AND/OR list). The explanations read them as the manual's lists of commands through `commandLists` and `withLists` (src/syntax/tree.ts): `command_list` nodes that are never in the tree, so `descendants` does not find them. A list over several lines of a body is a block (each line shows its part); at the top of a script, a newline ends a list.
- `test/bash-ast.test.ts` compares our tree with bash's own parser, through [bash-ast](https://github.com/cv/bash-ast) found in `$BASH_AST` or on `PATH` (skipped without it; CI runs it with the pinned release v0.3.3, and `BASH_EXPLAINER_BASH_AST=1` makes a missing binary fail). bash-ast is GPL-3.0: only run it as a separate program; never vendor, link or bundle it, add it to `package.json`, copy its code, or publish its binary. Accepted differences are in `test/fixtures/bash-ast-known.json`, each with a reason; the test also fails on a stale entry. `test/command-tokens.test.ts` runs the same way: every explanation token lies in one innermost command of ours that bash-ast has (known findings, and the counts it pins, in `test/fixtures/command-tokens-known.json`: update the counts when the corpus changes them).
- The fuzz test is seeded, and its inputs come from the corpus: adding snippets changes them and can expose a latent adapter bug. Fix the bug (with a test of the input); do not reseed.

## Tests that run bash

- To check whether something runs in a subshell, compare `$BASHPID` with `$$`; `$BASH_SUBSHELL` stays 0 in some subshells (`echo $BASH_SUBSHELL | cat`).
- A script that is generated (a differential or fuzz harness) or may recurse runs in a cgroup with `FUNCNEST` set, and is killed as a process group on a timeout: `systemd-run --user --scope -p MemoryMax=3G -p MemorySwapMax=0 -p TasksMax=500 …`, spawned `detached` and stopped with `process.kill(-pid)`. A generated `f() { ( f ); }` once forked until it filled the machine's memory, because the timeout killed only the outer `bash`.
- A tool can print differently when it runs under an agent: gh prints its full help after a usage error when `AI_AGENT` or `CLAUDECODE` is set, and only a short usage otherwise (as in CI). A comparison that passes locally can fail in CI; try it with those variables unset too.
- Feed a tool's stdin through `test/support/run.ts` (a file, not a pipe), so a tool that stops reading early cannot fail with EPIPE.
- In the web tests, type with `keyboard.insertText` (keys typed one by one can arrive out of order in CI), and wait for CodeMirror's selection layer, which is drawn on the next frame.
- A layout (and its test) must not depend on how wide the words are in a font: CI's Chromium draws Japanese with CJK fonts (IPAGothic, WenQuanYi, from `playwright install --with-deps`), and a machine without them draws boxes of another width. Wrap between groups that do not depend on text width, and check layouts with those fonts (`apt-get download fonts-ipafont-gothic fonts-wqy-zenhei`, `dpkg -x`, `FONTCONFIG_FILE`) at several widths and with long names.

## The semantic model

- The shell state along a script (set and shopt options, variables and their attributes, functions, aliases) comes from `shellState(tree, shell).at(node)` in `src/semantics/state.ts`, with a `run`, a `parse` and an `expand` state (aliases in `$( )`); `assigned` lists the variables some command sets. The analyzer does not scan the script for state. test/state-probes.test.ts compares it with bash on `test/fixtures/probes/state.json`; a fact it does not follow goes in the row's `gaps`, with the reason.
- Where a node runs comes from `shellState(tree, shell).env(node)` (`src/semantics/env.ts`): a chain of subshell, slot and call links, read with `processOf`, `whereOf` and `reachOf`; `slotEnvs` gives the chains of the commands a command's words run. The analyzer does not decide by itself what is a subshell; the walk and the chains share `subshellReasons` and `lastStageInShell`. test/env-probes.test.ts compares it with bash on `test/fixtures/probes/env.json` (a marker is a call of an exported function).
- What bash does to a word in its context (brace, tilde, splitting with the IFS in effect, globbing with the glob options in effect) comes from `wordMeaning(n, state)` and `partMeaning` in `src/semantics/words.ts`, and its fields from `wordFields`; the analyzer does not decide it from node types. test/word-probes.test.ts compares `wordFields` with bash on `test/fixtures/probes/words.json` (gaps as in state.json).
- What a command name runs comes from `resolveName(model, name, at, opts)` in `src/semantics/names.ts` (alias, keyword, function, builtin, file, with the definitions that do not apply and why), and what a prefix assignment does from `assignmentsOf`; the analyzer renders them and does not look up names itself. test/names-probes.test.ts compares it with `type -t` on `test/fixtures/probes/names.json`, gaps in each row's `gaps`.
- A statement's exit status and whether `set -e` stops the shell there come from `statusModel(state).status(n)` and `.errexit(n)` in `src/semantics/status.ts` (read from the run state: the walk turns errexit off in `$( )` without inherit_errexit, and in the functions called there, and the state says why, `ShellState.errexitWhy`), and its notes from `src/statusfacts.ts`, once per script; the analyzer does not decide them from node types. test/status-probes.test.ts runs `test/fixtures/probes/status.json` on an evaluator that reads the model (gaps as in state.json).
- What a condition always decides, and whether a statement runs only in dead code, come from `shellState(tree, shell).condition(n)` and `.dead(n)` (docs/design/semantics.md, 4.14); the analyzer does not decide conditions itself. They rely only on what `src/semantics/trust.ts` allows, an allow-list over the whole script (`blind` says why nothing is trusted). Its scan looks each construct up in the tables of `src/semantics/allow.ts` ([docs/design/trust-allow-list.md](docs/design/trust-allow-list.md)): a new builtin option, `set` or `shopt` option, bash variable, expansion operator or node type needs a row there, and a `followed` row names the probe rows or tests that check it (test/allow-list.test.ts). test/decisions.test.ts runs generated scripts in bash; a contradiction is a bug: fix it, with a test.
